# Chapter design: 'Search Ranking in Production: From Query to Result Page' — scope and spine
**Positioning.** This chapter is the applied complement to the vector-retrieval theory monograph and to DL-07 (encoder architectures). Those chapters answer *how do we score similarity and retrieve candidates efficiently*; this chapter answers *how do you run a search engine that people use* — the query side, the lexical machinery that still carries most production traffic, the behavioral-data flywheel, the ranking pipeline that fuses it all, and the measurement discipline that makes changes shippable. The framing device for the whole chapter is the **production search request lifecycle**:

```
query → [query understanding: classify, correct, tag, rewrite]
 → [retrieval: lexical (inverted index) ∥ dense (ANN) ∥ structured/KG]
 → [fusion + filtering + facet computation]
 → [L1 ranking: cheap features, thousands → hundreds]
 → [L2 ranking: LTR / cross-encoder, hundreds → tens]
 → [L3: personalization, blending, business rules, diversity]
 → [presentation: snippets, facets, answers/RAG]
 → [logging → judgments/signals → training data → back to top]
```

The last arrow is the chapter's thesis: **search is a closed-loop system**, and most staff-level interview differentiation happens in reasoning about the loop (bias, feedback, measurement), not the models.

# §1 The production search stack and the head/torso/tail framework
**Must-know items:**
- The full request lifecycle (diagram above) and typical latency budget allocation: ~5–10 ms query understanding, ~20–50 ms retrieval per source (parallel), ~10–30 ms L2 rerank, presentation assembly; p99 total commonly 100–300 ms for web/commerce.
- **Head/torso/tail decomposition** of query traffic (Zipfian): head queries (top ~1k–10k, huge traffic share) can be curated, cached, and heavily signal-boosted; torso queries have enough behavioral data for ML; tail queries (often 50–70% of *distinct* queries) have no history — this is where semantic retrieval, spell correction, and query relaxation earn their keep. Interviewers expect the strategy to *differ by segment*, not be uniform.
- Inverted index fundamentals at working depth: postings lists, doc values/columnar storage for faceting and sorting, near-real-time indexing and segment merges, why updates are append+merge, sharding by document with scatter-gather query fan-out, and the deep-pagination problem.
- The retrieval/ranking contract: retrieval is recall-oriented and must be cheap and decomposable (query-independent index); ranking is precision-oriented and can afford query-document interaction. Each stage bounds the next — the **recall ceiling** argument.
- Where business logic legitimately lives (L3): merchandising boosts, diversity/dedup (e.g., one result per seller/domain), compliance filtering — and why it must be *after* the learned ranker but *visible to evaluation*.

**Interview questions:**
- *Q: Your reranker offline NDCG improved 4% but online conversions are flat. Walk through the funnel diagnosis.* Sketch: (1) Check retrieval recall — maybe the reranker reorders a candidate set that lacks good docs (judged-only offline eval hides this). (2) Check judgment/click distribution mismatch — offline gains concentrated on torso queries that are a small traffic share, or on positions below the fold. (3) Check L3 overrides — business rules clobbering the new order. (4) Check offline eval contamination — click-derived labels inherit the old ranker's position bias, so "improvement" = agreeing with old system + noise. (5) Presentation: ranking change without snippet/title change may not change click behavior.
- *Q: Why not collapse the funnel into one giant cross-encoder over the whole corpus?* Sketch: cost — cross-encoder inference is O(corpus) per query with no precomputation (DL-07's decomposability argument); latency budget makes it infeasible beyond ~10²–10³ candidates. Also freshness and filtering are cheap in an inverted index and expensive to re-learn. The funnel is a cost-accuracy Pareto construction: each stage spends more per candidate on fewer candidates.

# §2 Query understanding
**Must-know items:**
- **Query classification/intent**: navigational vs informational vs transactional (web); in commerce: product-type/category intent, brand intent, browse vs targeted. Implementations: from logistic regression over character n-grams (latency-critical, must run in ~1–5 ms) to distilled BERT-tiny models. Intent gates downstream behavior: which verticals to query, whether to show facets, how aggressively to personalize.
- **Spell correction** as the noisy-channel model: argmax_c P(c)·P(q|c), candidates from edit-distance/keyboard-adjacency, language model P(c) from *query logs* (not documents — 'iphoen' → 'iphone' needs query priors); modern stacks use seq2seq or edit-tagging models. Key production nuance: *correction vs suggestion* thresholds (auto-correct high confidence, 'did you mean' otherwise) and never correcting matched rare terms (SKUs, names).
- **Query segmentation and tagging** (slot filling): 'nike red running shoes size 10' → brand=nike, color=red, product=running shoes, size=10. Turns unstructured queries into structured constraints against catalog attributes — the single highest-leverage commerce QU component. CRF/BiLSTM historically, small transformers now; trained from engagement-aligned catalog matches.
- **Entity recognition and resolution to the catalog/KG**: linking surface strings to canonical entities (brand disambiguation: 'apple'; location resolution). Requires alias tables mined from logs + embedding similarity + popularity priors.
- **Query rewriting/expansion**: synonym mining from (a) session reformulations (q1→q2 with eventual click), (b) queries sharing clicked documents (click bipartite graph), (c) embedding neighbors. Expansion recall vs precision trade-off; expansions should be *lower-weighted optional clauses*, not equal terms. **Query relaxation** for zero-result: drop lowest-IDF or unmatched constraint terms progressively.
- Where LLMs now sit: offline mining of synonyms/rewrites at scale, distilled into fast runtime models; direct LLM-in-the-loop only for conversational surfaces (latency).

**Interview questions:**
- *Q: Design spell correction for a commerce search engine. What breaks a naive dictionary approach?* Sketch: noisy channel with query-log LM; edit + phonetic candidates; per-language handling; the failure modes: correcting valid rare tokens (model numbers 'RTX 4090' → don't touch), context-dependent corrections ('dress shoos' vs 'shoo away'), and feedback contamination (log LM learns from uncorrected misspellings). Evaluate with correction acceptance rate + downstream zero-result/reformulation deltas, and precision on a curated no-touch list.
- *Q: How do you mine synonyms without an ontology?* Sketch: click-graph co-clicking (two queries clicking the same docs → candidate equivalence), session reformulation pairs filtered by success signal, embedding-space neighbors as candidates — then a precision filter (human or LLM validation) because click co-occurrence conflates synonymy with relatedness ('iphone case' ≠ 'iphone'). Deploy asymmetrically: expansion clause with a discount weight, measure with interleaving.
- *Q: When should query understanding change retrieval vs. only add ranking features?* Sketch: changes that alter the candidate *set* (segmentation→filters, expansion, relaxation, vertical routing) must happen at retrieval; signals that reorder (intent scores, entity confidence) work as LTR features. Retrieval-side changes are higher risk (can lose recall) → guard with zero-result and recall metrics.

# §3 Lexical relevance internals: BM25 mechanics and tuning
**Must-know items:**
- The BM25 formula and *the intuition of each part*: score(q,d) = Σ_t IDF(t) · f(t,d)(k1+1) / (f(t,d) + k1·(1−b+b·|d|/avgdl)). **k1** (~1.2 default) controls term-frequency saturation — the score is concave in TF, asymptoting at IDF·(k1+1): the 10th occurrence of a term adds almost nothing (the fix for TF-IDF's linear-TF spam vulnerability). **b** (~0.75) controls length normalization: b=0 ignores doc length, b=1 fully normalizes. Tuning intuition: short structured fields (titles, product names) want low b and low k1 (presence ≈ binary); long prose wants defaults.
- Lucene's IDF = ln(1 + (N−n+0.5)/(n+0.5)) and why the +0.5 smoothing / why classic probabilistic IDF can go negative.
- **Field weighting done right**: naive per-field BM25 scores summed with boosts (what Lucene/dismax does) vs **BM25F**, which combines *weighted term frequencies across fields before saturation*. The interview-worthy insight: with per-field-then-sum, a term appearing once in title and once in body double-dips two unsaturated curves; BM25F saturates jointly. Dismax's `tie` parameter (max vs sum of field scores) as the practical compromise; typical stack: title^3 brand^2 body^1 + phrase-match boosts.
- **The analysis chain** and its relevance consequences: tokenization, lowercasing, stemming (Porter aggressive vs light) vs lemmatization, stopwords (mostly keep them now, rely on IDF), synonyms at index-time (cheap queries, reindex to change, multi-word terms break positions) vs query-time (flexible, slower); shingles/edge-ngrams for partial and prefix match. Mismatched index/query analyzers as the classic silent relevance bug.
- **Boolean structure**: minimum_should_match as the recall/precision dial ('2<75%' idioms), phrase and proximity boosts (pf/pf2/pf3-style), why AND-semantics + relaxation-on-zero-results is the common commerce pattern.
- Function/boost queries: multiplicative vs additive boosts for freshness/popularity — additive boosts distort differently across score ranges; log-scaling popularity; and why hand-tuned boost soup is what LTR eventually replaces.

**Interview questions:**
- *Q: Explain what k1 and b do, and give a case where you'd change each from defaults.* Sketch: as above. Lower b for title-like fields (length variation is noise); raise k1 for long documents where repeated mentions genuinely indicate aboutness; b↑ if long boilerplate-heavy docs dominate results. Mention that tuning should be validated against a judgment list, grid-searching k1∈[0.5,2], b∈[0.3,1].
- *Q: Your product search matches 'red dress' to a doc titled 'red' with 'dress' buried in a long description, above an exact 'red dress' title match. Diagnose.* Sketch: per-field sum double-dipping + no phrase boost + length normalization diluting the description match oddly. Fixes: phrase/proximity boost on title, BM25F-style combination or dismax with tie≈0, minimum_should_match on the title field, or a 'all-terms-in-title' boolean boost feature. This is the canonical 'do you actually understand lexical scoring' probe.
- *Q: Index-time vs query-time synonyms — trade-offs?* Sketch: index-time: fast queries, terms get IDF of the merged class, but reindex to update and multi-word synonyms corrupt position/phrase queries; query-time: instant updates, correct phrase handling with graph token filters, but query expansion cost and IDF asymmetry (expanded rare term inherits its own IDF). Production pattern: high-confidence symmetric synonyms at index time, tail/experimental ones at query time with weights.

# §4 Behavioral signals and click models
**Must-know items:**
- Click data is the largest and cheapest relevance signal and it is **biased and missing-not-at-random**: position bias (examination decays with rank; position 1 gets 3–10× the clicks of position 5 at equal relevance), presentation bias (snippet/image quality), trust bias (users trust top results), selection bias (only retrieved docs get feedback). Core maxim: **not-clicked ≠ irrelevant** — it usually means not-examined.
- **Formal click models**: Position-Based Model (PBM): P(click)=P(examined | position)·P(attractive | q,d) — factorizes propensity from relevance. Cascade model: sequential examination top-down, stop at first click (explains why skips above a click are informative — Joachims' 'clicked > skipped-above' pairwise preferences). Dynamic Bayesian Network (DBN): separates *attractiveness* (click) from *satisfaction* (no return-to-SERP after click) — introduces dwell/last-click semantics. Know which assumptions break where (PBM: no sequential dependence; cascade: single click only).
- **Propensity estimation**: result randomization (swap adjacent pairs — RandPair; or FairPairs), intervention harvesting from natural ranker variation, or jointly learning propensity+relevance (regression EM, dual learning). Then **counterfactual LTR**: inverse-propensity-scored loss w_i = 1/P(examined at pos_i), clipping to control variance, doubly-robust estimators as the variance/bias compromise.
- **Signals boosting** (the Grainger/Turnbull workhorse): aggregate per (query, doc) engagement — clicks, add-to-carts, purchases, dwell — into a memorized prior served as a boost or LTR feature. Design details that interviews probe: signal decay half-life (seasonality, freshness), weighting purchases ≫ clicks, sparsity back-off (query → query-category → global doc popularity), spam/manipulation resistance (dedupe by user, bot filtering), and the cold-start/feedback-loop hazard: boosted items collect more signals — rich-get-richer.
- Beyond clicks: dwell time thresholds (short-click = bad), add-to-cart/purchase (sparser but cleaner), query reformulation as negative signal, 'good abandonment' (answer on SERP) as a confound.

**Interview questions:**
- *Q: You train a ranker on raw click-through labels and offline AUC looks great. Why is this circular, and fix it.* Sketch: labels inherit the current ranker's positions → model learns 'predict what was ranked high' → offline metric rewards replicating production. Fixes: (1) IPS-weight by estimated examination propensity, (2) add position as a training feature and set it to a fixed value at serving ('position debiasing by feature'), (3) collect a small randomized-traffic slice for unbiased eval, (4) editorial judgment list as the anchor. Expected to name at least propensity weighting and the randomization source.
- *Q: Design the signals-boosting pipeline for a marketplace: what aggregations, what decay, what failure modes?* Sketch: streaming aggregation of (query_normalized, item) → weighted engagement score with exponential decay (half-life days–weeks by category velocity); normalize by impressions to get rates, floor on impression count (Wilson/Bayesian smoothing for low-traffic pairs); back-off hierarchy for tail queries; guard against self-reinforcement by capping the boost's share of total score and reserving exploration slots; monitor per-segment lift and diversity metrics.
- *Q: PBM vs cascade vs DBN — which would you use to interpret logs where users click multiple results?* Sketch: cascade assumes single click → violated; PBM handles multiple clicks but ignores order; DBN/UBM model click sequences with satisfaction. Practically: PBM propensities are what feed IPS-LTR because they factorize cleanly; DBN's satisfaction variable is how you convert click+dwell into graded pseudo-labels.

# §5 Learning to rank end-to-end
**Must-know items:**
- **The three loss families with their real trade-offs**: pointwise (regress/classify per doc: calibrated scores — required for ads bidding and score thresholds — but optimizes the wrong objective for ordering); pairwise (RankNet: P(i≻j)=σ(s_i−s_j), optimizes inversions but treats all inversions equally — an inversion at rank 50 counts like one at rank 1); listwise/LambdaRank: scale each pairwise gradient by |ΔNDCG| of swapping the pair — **this is THE mechanism to be able to explain**: it back-propagates the metric's position discount without needing NDCG to be differentiable. LambdaMART = these lambda gradients driving gradient-boosted trees.
- **Why LambdaMART is still the default** for feature-vector ranking: GBDTs dominate on tabular/heterogeneous features (mixed scales, missing values, monotonic-ish relations, small-to-medium data), train in minutes, are cheap at inference. **Neural LTR wins when** raw text/embedding interactions matter, data is huge, or you want joint training with encoders. The modern compromise: GBDT over features *including* dense-similarity scores from a bi/cross-encoder. Cite-able: multiple studies (and the Yahoo LTR challenge legacy) show tuned LambdaMART matching or beating neural rankers on standard feature sets.
- **Feature taxonomy**: query-only (length, intent scores, IDF stats), document-only (popularity, freshness, quality/pagerank-ish, price, rating), query-document (BM25 per field, phrase-match flags, term coverage, embedding cosine, click-signal priors, historical CTR), context (device, locale). Plus feature hygiene: leakage (using post-click signals computed over the eval window), coverage skew between head and tail, online/offline parity (the feature-store consistency problem from DL-17).
- **Training-data construction**: group by query; labels from (a) graded editorial judgments, (b) debiased clicks (§4), (c) blended. Sample queries stratified by traffic *and* by segment (head/tail, category); include enough negatives per query (impressed-but-not-engaged + random); temporal split, never random-by-row (leaks query duplicates across train/test).
- Serving: L1 (linear/small GBDT, hundreds of ns/doc) vs L2 (full model) split; score caching; monotonicity constraints for guardrail features (price, rating) as a robustness/merchandising tool.

**Interview questions:**
- *Q: Explain the lambda in LambdaMART. Why not optimize NDCG directly?* Sketch: NDCG is piecewise-constant in scores (rank permutations) → zero/undefined gradients. LambdaRank's move: define gradients directly (λ_ij = −σ·|ΔNDCG_ij| / (1+e^{σ(s_i−s_j)})) rather than a loss; pairs whose swap would move NDCG most get the largest push. Empirically (and later shown more formally) this ascends NDCG. In MART, the λ's are the pseudo-residuals each tree fits. Strong candidates note this concentrates learning on top-of-list errors.
- *Q: When would you insist on a pointwise objective despite ranking being the task?* Sketch: ads/auction — expected-value bidding needs calibrated pCTR (DL-12's calibration section); any thresholded decision (show/hide, minimum-quality gate); multi-surface score comparability. Pattern: calibrated pointwise model + listwise reranker on top, or post-hoc calibration (Platt/isotonic) of a ranking model, noting pairwise/listwise training destroys calibration.
- *Q: Your LTR model degrades tail-query relevance while improving overall NDCG. Why, and what do you change?* Sketch: training data and click features are head-dominated; click-prior features are empty for tail (coverage skew) and the model over-relies on them. Fixes: stratified query sampling and per-segment eval slices, back-off feature design, separate tail model or segment feature, more weight on content features (BM25, embeddings) that generalize.
- *Q: Editorial labels say doc A > B; click data says B ≫ A. Which do you trust?* Sketch: inspect for presentation bias (B has better image/price shown), judgment-guideline gaps (judges lack purchase context — 'relevant' vs 'what users buy'), or freshness. Neither is ground truth: editorial measures topical relevance, behavior measures utility. Production answer: use editorial for retrieval/topicality gates, behavioral for final ordering, and reconcile systematic disagreements by fixing guidelines — a staff-level 'measurement is a system' answer.

# §6 Semantic search integration and hybrid retrieval
**Must-know items:**
- The case for hybrid: lexical fails on vocabulary mismatch (tail, conceptual queries); dense fails on exact identifiers (SKUs, model numbers, names, negation) and out-of-domain drift. Their error sets are complementary — empirically hybrid > either alone on most benchmarks (BEIR-era result).
- **Fusion mechanics — the interview classic**: raw score summation fails because BM25 is unbounded/query-dependent while cosine is [−1,1] with query-dependent concentration; min-max/z-score per-query normalization is unstable on small candidate sets. **Reciprocal Rank Fusion**: Σ_sources 1/(k + rank), k≈60 — rank-based, scale-free, shockingly robust. Beyond RRF: learned linear fusion, or (best) *union candidates and let the L2 ranker fuse* using both scores as features — fusion becomes a ranking-feature problem.
- Learned sparse (SPLADE/docT5query-style doc expansion) as the middle path: inverted-index serving + learned term weighting, closes vocabulary mismatch while keeping exact-match precision and cheap filtering.
- **Filters × ANN**: pre-filtering (filter then search — exact but breaks HNSW graph connectivity on selective filters) vs post-filtering (search then filter — recall collapses when filter is selective); production engines do adaptive strategies / filtered-HNSW. Lexical engines get filtering for free — a real reason hybrid stacks keep the inverted index authoritative for constrained queries.
- Embedding lifecycle in production: domain fine-tuning (from click pairs — in-batch negatives + hard negatives from BM25, per NLP-09's DPR treatment), index rebuild vs incremental upsert, embedding-version skew between query and doc towers during rollouts, drift monitoring.
- When NOT to add dense retrieval: strong structured/attribute queries, tiny corpora, teams without eval infrastructure — 'hybrid' doubles operational surface.

**Interview questions:**
- *Q: Why does naive score fusion (0.5·BM25 + 0.5·cosine) misbehave, and what do you do instead?* Sketch: incompatible scales and query-dependent distributions (a rare-term query inflates BM25 for all candidates); normalization per query over top-k is noisy. RRF for a first ship; then treat both scores as LTR features so fusion weights are learned per feature interaction (query length, intent). Expected to name RRF and its k constant's role (dampens top-rank dominance).
- *Q: Dense retrieval tanks on queries containing part numbers. Fix without abandoning it.* Sketch: hybrid union guarantees lexical candidates survive; add exact-match/term-coverage features to the reranker; optionally detect identifier-like tokens in QU and route/boost lexical; hard-negative fine-tuning with identifier-swapped negatives teaches the encoder that 'X100' ≠ 'X200'. Shows understanding that embeddings blur near-identical strings by construction.
- *Q: A selective metadata filter (seller_id) makes ANN recall collapse. Explain and fix.* Sketch: post-filtering discards most of top-k; pre-filtering on HNSW traverses a graph whose neighbors are mostly filtered-out (connectivity loss). Fixes: per-partition indexes for common filters, filtered-search algorithms (evaluate filter during traversal with expanded ef), IVF with filter-aware probing, or route selective-filter queries to the inverted index entirely.

# §7 Personalization and recommendations-in-search
**Must-know items:**
- **The cardinal rule: query intent dominates.** Personalization reorders within relevance-equivalent sets; it must never override explicit intent (searching 'android phone' as an iPhone owner). Implementation: personalization features enter late (L2/L3), often with capped score contribution, or as a tie-breaking blend.
- Personalization signal taxonomy: session-level (current-session clicks/cart — highest value, no cold-start for the *session*), short-term history, long-term profile (category/brand affinities, size/format preferences), demographic/geo (locale, shipping). Sequence models (SASRec-style, DL-12) to encode history; user-tower embedding dot-product as an L2 feature.
- **Recs-in-search surfaces**: null/zero-query state (home = pure recs), related searches, 'similar items' on low-recall results, complementary recs post-add-to-cart, query autocomplete personalization (careful: privacy leaks in suggestions). Each surface is a different objective (discovery vs task completion).
- Marketplace two-sidedness: exposure fairness across sellers, diversity injection (MMR-style or slot constraints), exploration for new items/sellers (epsilon slots or Thompson sampling on engagement priors) — and the argument for *why* exploration is not charity: without it the signals loop (§4) starves new inventory and long-term marketplace health decays even as short-term CTR looks fine.
- Measurement asymmetry: personalization gains are heterogeneous — measure per-cohort (heavy vs new users), and beware the feedback loop of profiles trained on personalized exposure (filter-bubble dynamics: the profile narrows because exposure narrowed).

**Interview questions:**
- *Q: Where in the search stack do you inject personalization, and why not at retrieval?* Sketch: retrieval-stage personalization (personalized ANN query vector) risks recall damage for explicit intent and makes caching impossible (query results no longer shareable across users — head-query caching is a huge cost lever). Standard: candidate set stays intent-driven (plus perhaps a small personalized candidate source), personalization features in L2, blending/diversity in L3. Exception: zero/broad-intent queries ('shoes', empty query) where personalization legitimately drives candidates.
- *Q: Personalized search improved engagement for power users, flat for new users, and marketplace listing diversity dropped 8%. Ship it?* Sketch: staff-level answer is a multi-objective negotiation: check long-term holdout for ecosystem effects, add exposure/diversity guardrails, consider triggering personalization only above a profile-confidence threshold (fixes new-user dilution), and quantify seller-side concentration (Gini on impressions). Shipping engagement +X% while quietly concentrating exposure is the trap.
- *Q: How do you personalize without per-user latency blowups?* Sketch: user embedding precomputed (batch or near-real-time via streaming session encoder), fetched from a feature store in parallel with retrieval; dot-products against candidate embeddings are cheap at L2 scale; session features computed client- or edge-side. Keep the heavy sequence model offline; online it's a lookup.

# §8 Relevance judgment: editorial, crowd, and LLM-assisted
**Must-know items:**
- Why a judgment program exists at all: behavioral data can't evaluate what wasn't shown (selection bias) and can't distinguish attractiveness from relevance; judgments are the *unbiased anchor* for offline eval and LTR labels.
- **Graded scales and guidelines**: typical 4–5 point scales (e.g., 0 bad / 1 related / 2 relevant / 3 highly relevant / 4 perfect-navigational); the guideline document is the real asset — it encodes product policy (does 'compatible accessory' count for a device query?). Google's Search Quality Rater Guidelines as the canonical public example (needs-met × page-quality dual rating).
- **Crowdsourcing mechanics**: qualification tests, golden/honeypot tasks for ongoing quality control, ≥3-way redundancy with adjudication of disagreements, per-judge reliability scores, task design (show the query context: locale, device). **Agreement statistics**: Cohen's/Fleiss' kappa, Krippendorff's alpha for ordinal scales; realistic kappa for relevance is ~0.4–0.6 — disagreement is signal about guideline ambiguity, not just noise.
- **Pooling** for judgment coverage: judge the union of top-k across systems (TREC pooling); the unjudged-document problem when a new system retrieves outside the pool (§9's condensed-list issue).
- **LLM-assisted judgment**: LLMs now match or exceed crowd agreement with expert judges on topical relevance (the post-2023 consensus; e.g., Bing/TREC experiments). Recipe: detailed rubric prompt mirroring the human guidelines, structured output, calibration set of expert-labeled pairs to measure LLM-vs-expert kappa, human adjudication of low-confidence/disagreement cases. Failure modes: self-preference when evaluating LLM-rewritten content, systematic blind spots (freshness, locale nuance, factuality), and the circularity hazard of using the same model family in ranking and judging. Economics: 10–100× cheaper → judge far more (q,d) pairs → denser training data for LTR.

**Interview questions:**
- *Q: Design the relevance judgment program for a new vertical (say, grocery search). What do you decide first?* Sketch: (1) the guideline: define relevance for the domain (substitutability matters: 'oat milk' for 'milk'?), graded scale, edge-case policy; (2) query sampling: stratified by traffic decile + category + zero-click segments; (3) pooling depth across current systems; (4) judge mix: small expert core writes/maintains guidelines and adjudicates, crowd/LLM for volume; (5) QC: honeypots, kappa monitoring, guideline iteration loop. Numbers: a few thousand queries × ~20–50 judged docs each is a serviceable eval set.
- *Q: Your LLM judge agrees with experts at kappa 0.65 while crowd workers hit 0.55. Do you drop the crowd?* Sketch: mostly yes for topical relevance at scale, but keep humans for: guideline development (LLMs can't set product policy), auditing LLM systematic biases (sample-based human review of LLM labels), locale/cultural coverage where the model is weak, and any judgment that feeds back into evaluating LLM-generated features (independence). Also: agreement with experts on *current* data ≠ robustness to distribution shift — keep a rolling expert calibration set.
- *Q: Judges rate a result 'perfect' but users never click it. What are the hypotheses?* Sketch: presentation problem (bad title/image/price display), judgment context mismatch (judges see full page, users see snippet), attractiveness vs relevance gap, position (it's shown low — check propensity-adjusted CTR), or the guideline optimizes topicality while users optimize utility (price!). The meta-point: judgments and behavior measure different constructs; investigate before 'fixing' either.

EXISTING COVERAGE: DL-18 §Human Evaluation (:346) and §LLM-as-judge (:360) cover generic human-eval and LLM-judge biases (verbosity, position, self-enhancement) in the *generation-evaluation* context; NLP-10 similarly. GENUINELY NEW: everything search-specific — graded relevance scales and guideline design, crowdsourcing QC mechanics (honeypots, kappa norms for relevance), TREC-style pooling, LLM-as-relevance-judge with calibration-against-experts methodology, and judgments as an LTR data supply chain. No existing chapter treats judgment collection as an owned system.

# §9 Search evaluation: offline regimes and online experimentation
**Must-know items:**
- **NDCG regimes** — beyond the formula (DL-18 has it): choice of k (NDCG@5/@10 for SERP-visible quality; @50 for reranker headroom), gain function (linear vs exponential 2^rel−1 — exponential heavily rewards top grades; know which your org uses), and the **unjudged-document problem**: treating unjudged as irrelevant penalizes novel systems; condensed lists (remove unjudged) inflate them; bpref/inferred measures or judging deltas (judge what the new system newly retrieves) as remedies. Per-stage metrics: recall@k against judged-relevant for retrieval; NDCG/ERR for ranking; MRR for navigational/known-item.
- Slice everything: head/torso/tail, query intent class, market/language, new vs tenured content. A single aggregate NDCG hides regressions interviewers will ask about.
- **Online metric hierarchy**: (1) direct engagement: CTR@k, success/click-through with dwell threshold ('long click'), zero-result rate, abandonment split into good (answer on page) vs bad, reformulation rate, time-to-first-click; (2) task/business: conversion, add-to-cart, revenue per search, session success; (3) ecosystem guardrails: diversity, new-content exposure, latency (latency is a relevance metric — +100ms measurably reduces engagement). Anti-pattern to name: raw CTR as a north star (rewards clickbait/attractiveness).
- **Interleaving**: team-draft interleaving (rankers alternate drafting results into one list; clicks credit the drafting team) — 10–100× more sensitive than A/B because it's within-user/within-query, so use for cheap ranking-change triage. Limitations: only compares rankings (no UI/latency effects), no absolute business-metric magnitude, credit assignment breaks with heavy presentation differences → the standard funnel: offline judgment eval → interleaving → full A/B for the finalists.
- A/B specifics for search: query-level vs user-level randomization (user-level for personalization/learning effects), novelty/primacy effects, experiment interference via shared trained models (the treatment model trains on treatment traffic — beware), long-term holdouts for ecosystem health.

**Interview questions:**
- *Q: Compute NDCG@3 by hand for grades [3,0,2] against ideal [3,2,0], exponential gain.* Sketch: DCG = 7/1 + 0 + 3/2 = 8.5 (discounts 1/log2(r+1): 1, 0.631, 0.5); IDCG = 7 + 3·0.631 = 8.893; NDCG ≈ 0.956. Candidates who can't do this arithmetic on a whiteboard fail the screen — that's why it's here.
- *Q: Your new retriever surfaces many unjudged docs and offline NDCG drops. Is the system worse?* Sketch: unknown — unjudged≠irrelevant. Options: judge-the-delta (send new-system-only docs for judgment — the standard practice), report condensed-list metrics alongside as bounds, check behavioral proxies. Meta-answer: pooled judgment sets are biased toward incumbent systems; a novel retrieval paradigm (dense vs lexical) is exactly when this bias bites hardest.
- *Q: When would interleaving mislead you relative to A/B?* Sketch: treatment changes result *presentation* or latency (interleaving hides both); metrics beyond clicks (revenue, long-term retention) matter; rankings differ radically so the interleaved list is incoherent to users; personalization treatments where the unit of analysis is the user. Also interleaving can't measure zero-result/recall changes — it needs both rankers to produce lists.
- *Q: Define 'good abandonment' and why it complicates your metrics.* Sketch: user satisfied without clicking (answer box, phone number, price visible on SERP). Naively counts as failure → penalizes the best SERP features. Mitigations: instrument on-SERP interactions (copy, hover, dwell-on-page), model-based satisfaction inference, or task-completion surveys. Increasingly central in the RAG-answer era (§10) where the *ideal* outcome is zero clicks.

EXISTING COVERAGE: DL-18 §Ranking Metrics (:148) defines NDCG/MRR/MAP/Recall@K and the offline-online gap (:454); DL-17 covers A/B testing thoroughly and has the interleaving paragraph (:271–277) with the sensitivity claim; NLP-09 §Retrieval Metrics covers recall@k/MRR for RAG. GENUINELY NEW: NDCG regime choices (k, gain base, unjudged handling — condensed lists, judging deltas), per-stage and per-slice measurement discipline, the search-native online metric family (zero-result, good/bad abandonment, reformulation, time-to-click, revenue-per-search), team-draft interleaving mechanics and its limitation list, query- vs user-level randomization, and the offline→interleave→A/B promotion funnel.

# §10 Conversational and RAG-era search; LLM-augmented ranking
**Must-know items:**
- The result page is becoming an **answer engine**: retrieval feeds synthesis (RAG over the live index) with citations; classic ranking survives *inside* as the retrieval layer whose precision@k now directly bounds answer faithfulness. Consequence: top-k precision matters more, whole-page NDCG less; 'good abandonment' becomes the success case, breaking click-based training data supply — a strategic point interviewers at frontier labs probe (where does future training signal come from when users stop clicking?).
- **Conversational query understanding**: rewrite the current turn into a self-contained query using dialog history (coreference: 'how much does *it* cost'); trained rewriters (T5-class, distilled from LLM rewrites) since full-history dense retrieval underperforms explicit rewriting; session state = entity/constraint stack (slot carryover, constraint revision: 'actually under $50').
- **LLM rerankers**: pointwise relevance generation (grade each doc, calibrate via token logprobs), pairwise (expensive, O(n²) or sorting-based), **listwise sliding-window** (RankGPT pattern: rank ~20 at a time, slide bottom-up) — zero-shot LLM listwise reranking beats fine-tuned cross-encoders on many benchmarks but at 10–1000× cost → **distill** into a cross-encoder/small LTR model for production; LLM stays offline as the teacher and judge (§8). Same trio of judge biases (position within prompt, self-preference) applies.
- LLMs in the ranking *feature* pipeline: offline enrichment (doc summaries, generated queries/docT5query-style expansion, attribute extraction into facets), synthetic training data (query generation for tail domains — how modern embedding models are trained), and relevance labels (§8) — the cheap, robust wins vs online LLM calls.
- Generative retrieval (DSI-style: model emits doc identifiers) as a known research direction with unresolved updatability/scale issues — one-paragraph awareness level.
- Evaluation shift: retrieval metrics + answer faithfulness/citation precision (bridge to NLP-09 RAGAS coverage); adversarial surface: prompt injection via retrieved web/marketplace content (SEO evolves into 'GEO' — content written to manipulate the synthesizer).

**Interview questions:**
- *Q: Add an answer layer on top of an existing e-commerce search. What changes in the ranking stack and its metrics?* Sketch: retrieval now optimizes precision@small-k with faithfulness-grade content (spec sheets over listicles); need answerability classification in QU (route: answer vs classic SERP); metrics move to answer correctness/citation-support + task completion, with click supply for training dropping → invest in judgment/LLM-label pipelines; latency budget explodes → streaming, caching of head answers, small distilled synthesizer. Also name the injection risk from seller-controlled content.
- *Q: RankGPT-style listwise reranking beats your cross-encoder offline by 3 NDCG points but costs 200× more. Production plan?* Sketch: distillation — LLM ranks a large query sample offline, train the cross-encoder (or GBDT feature) on those orderings (RankNet loss over teacher pairs); keep the LLM as a continuous offline teacher/judge on fresh traffic samples; optionally serve LLM reranking only for tail/zero-signal queries or high-value sessions. Expected: recognize the teacher-student pattern rather than choosing either extreme.
- *Q: Multi-turn shopping conversation: user says 'show me cheaper ones from the second brand.' What does your query pipeline need?* Sketch: dialog state tracking of the result context (which brands were shown), reference resolution against *results* not just text, constraint stack update (price ceiling relative to shown items), rewrite into structured query (brand=X, price<Y, product carried over) hitting the same retrieval stack. Points for noting the state lives server-side keyed to session and that evaluation needs conversation-level success metrics.

# §11 Faceted search and knowledge graphs (where still relevant)
**Must-know items:**
- **Facets** = structured refinements with counts, computed via doc-values/columnar aggregations over the *matching set* (post-filter counting semantics: a selected facet value shouldn't zero out its siblings' counts — multi-select facet count semantics is a classic gotcha). Facet *selection and ordering* is itself a ranking problem: which attributes to show for this query (category-dependent: 'size' for shoes, 'capacity' for drives) — learn from refinement engagement.
- Facets are the structured consumer of §2's query tagging: tagged constraints pre-apply filters; conversely applied facets should feed back into ranking (a filtered attribute is a strong intent signal).
- **Knowledge graphs where they still earn their keep**: (1) entity-centric SERPs (entity panels, disambiguation); (2) commerce attribute normalization (brand hierarchies, compatibility graphs: 'fits iPhone 15'); (3) enterprise/healthcare where ontologies are mandated (UMLS); (4) related-entity recommendation ('people also search for') via graph proximity. What faded: hand-built ontologies as the primary semantic layer — embeddings ate general semantic matching; the durable role is *precision infrastructure*: exact attributes, relationships, and constraints that embeddings blur.
- Content-mined 'semantic knowledge graphs' (the Grainger emphasis): term-association graphs from the corpus/logs powering related-term suggestion and query classification — modern take: these pipelines are now cheaper via embeddings/LLM extraction, but the serving-side idea (graph of entities/terms with weighted edges consulted at query time) persists.
- Structured + unstructured hybrid queries ('red running shoes under $50 similar to these'): boolean/range filters from tagging + vector similarity + lexical — the tri-modal query as the realistic modern commerce request, and why the engine choice (Elasticsearch/OpenSearch/Vespa vs pure vector DB) hinges on it.

**Interview questions:**
- *Q: Design faceted navigation for 100M-product search. Where do facet counts get expensive and what are the fixes?* Sketch: counts require aggregating over full match set (not top-k) → doc values + per-shard aggregation + merge; expensive for high-cardinality attributes → approximate counts/top-N values, cache head-query facets, restrict candidate attributes by predicted category. Cover multi-select semantics (compute each facet's counts excluding its own filter) and facet ordering as learned ranking.
- *Q: When would you invest in a knowledge graph vs relying on embeddings?* Sketch: KG when you need *guaranteed* precision and explainability on relations — compatibility, hierarchies, regulatory constraints — or joins across structured data; embeddings for fuzzy semantic matching. The strong answer: they compose — KG normalizes attributes that become filters and features; embeddings handle the residual unstructured match; and LLMs have collapsed the KG *construction* cost (extraction from product descriptions), reviving KG ROI.

EXISTING COVERAGE: DL-13 (graph neural networks) covers graph ML but not KG-for-search; NLP-09 mentions metadata filtering (:596) and NLP-11 covers entity linking generically. GENUINELY NEW: essentially all of it — facet computation/count semantics, facet selection as ranking, query-tagging→filter integration, the honest 'what KGs are still for' assessment, tri-modal structured+lexical+vector queries and engine selection. Deliberately the shortest section — weight reflects current interview frequency (facets come up in every commerce system-design interview; KG theory rarely).

# The ten search-specific fumble tests (questions that end interviews when missed)
These are the items experienced search interviewers use as competence gates — fumbling any one of them reliably caps the level or ends the loop. Each is stated as the test plus the sentence a passing candidate must be able to produce.

1. **BM25 parameter intuition.** Test: 'What do k1 and b do?' Must produce: k1 = term-frequency saturation (concave TF, asymptote at IDF·(k1+1)); b = document-length normalization strength; and one example of when to move each. Reciting the formula without the saturation intuition is a fail.
2. **Bi-encoder vs cross-encoder economics.** Test: 'Why not cross-encode everything?' Must produce: bi-encoder scores decompose → precompute doc embeddings + ANN, O(1)-ish per query; cross-encoder requires joint inference per (q,d) pair → only affordable over the reranking window; quality gap comes from query-document term interaction.
3. **Position-bias circularity.** Test: any question involving training on clicks. Must produce, unprompted: clicks are confounded by position/examination; training on raw clicks teaches the model to reproduce the current ranker; name a fix (IPS with estimated propensities, position-as-feature-zeroed-at-serving, randomized data slice). Not raising it unprompted is the single most common staff-level fail.
4. **The lambda in LambdaMART.** Test: 'How does LambdaMART optimize NDCG when NDCG isn't differentiable?' Must produce: pairwise gradients scaled by |ΔNDCG| of swapping the pair — gradients defined directly rather than derived from a loss; trees fit these pseudo-residuals.
5. **NDCG by hand + the unjudged-document trap.** Test: small numeric example, then 'new system retrieves unjudged docs.' Must produce: correct arithmetic (gain/discount/normalize) AND 'unjudged ≠ irrelevant; judge the delta or report condensed-list bounds.'
6. **Why raw hybrid score fusion fails.** Test: 'Combine BM25 and cosine scores.' Must produce: incompatible, query-dependent score distributions (BM25 unbounded); use rank-based fusion (RRF: Σ1/(k+rank)) or learn the fusion as reranker features. Proposing 0.5/0.5 weighted sum without flagging normalization is a fail.
7. **The retrieval recall ceiling.** Test: any funnel design or 'offline gain, online flat' debugging. Must produce: no downstream ranker can recover a document the retrieval stage missed → measure recall@k *per stage* against judged-relevant, and diagnose funnels stage-by-stage.
8. **Interleaving vs A/B.** Test: 'How do you test a ranking change cheaply?' Must produce: team-draft interleaving — same user sees a merged list, clicks credit the source ranker — ~10–100× sample-efficiency over A/B because within-user variance cancels; but it only compares rankings (no latency/UI/business-metric effects), so finalists still go to A/B.
9. **Not-clicked ≠ irrelevant (implicit feedback semantics).** Test: any negative-sampling or label-construction question. Must produce: unclicked results are mostly unexamined (missing-not-at-random); distinguish impressed-skipped (weak negative, especially skipped-above-a-click) from never-shown (unknown); pure random negatives make training too easy, pure impressed negatives inherit bias — mix, and add hard negatives for encoders.
10. **Feedback loops and exploration.** Test: 'Your engagement-trained system's metrics look great; what breaks in six months?' Must produce: the ranker curates its own future training data → popularity/self-reinforcement spiral, starved new content, narrowing personalization; remedies: exploration traffic (epsilon slots/Thompson sampling), randomization for unbiased data, long-term holdouts, diversity/new-content guardrail metrics.

Pedagogical note for the chapter: print these as the closing checklist, each cross-referenced to its section (1→§3, 2→DL-07, 3→§4, 4→§5, 5→§9, 6→§6, 7→§1, 8→§9, 9→§4/§5, 10→§4/§7), mirroring the interview-question format the books already use.
