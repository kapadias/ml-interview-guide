\chapter{Graph Neural Networks}
\label{chap:graph_neural_networks}

\begin{tldr}
Graph neural networks extend deep learning to non-Euclidean data---social networks, molecules, transaction graphs, knowledge bases---where entities are nodes and relationships are edges. The core idea is simple: iteratively update each node's representation by aggregating information from its neighbors (message passing). This chapter covers when to reach for GNNs instead of tabular or sequence models, the key architectures (GCN, GraphSAGE, GAT, GIN) and their trade-offs, the critical challenge of over-smoothing, scalability techniques for billion-node graphs, and practical applications. GNNs appear less frequently in interviews than transformers but are a strong differentiator for Staff+ candidates---especially for fraud detection, recommendation, and molecular design questions.
\end{tldr}

%==============================================================================
\section{When to Use GNNs}
\label{sec:when_gnns}
%==============================================================================

Not every relational dataset needs a GNN. Most candidates reach for GNNs too eagerly. The first question should always be: \textit{does the graph structure carry signal that a flat model would miss?}

\subsection{Graph Representation Basics}

A graph $G = (V, E)$ consists of nodes $V$ and edges $E$. Each node $v$ may have features $\vx_v \in \R^d$. Edges can be directed or undirected, weighted or unweighted, and may carry their own features. The structure is typically represented as an adjacency matrix $\mA \in \R^{|V| \times |V|}$ or, more practically, as edge lists.

\textbf{Common graph types in ML:}
\begin{itemize}
    \item \textbf{Homogeneous:} One node type, one edge type (social follow graph)
    \item \textbf{Heterogeneous:} Multiple node types, multiple edge types (user-item-store graph in e-commerce)
    \item \textbf{Bipartite:} Two node types, edges only between types (user-item interactions)
    \item \textbf{Temporal:} Edges have timestamps (transaction networks, communication graphs)
    \item \textbf{Knowledge graph:} Directed, labeled edges as (head, relation, tail) triples
\end{itemize}

\begin{keyinsight}{GNNs Add Value When Neighbors Are Informative}
The fundamental assumption behind GNNs is \textit{homophily}: connected nodes tend to share labels or properties. A fraudster's neighbors are more likely to be fraudsters. A molecule's biological activity depends on how its atoms are bonded, not just which atoms are present. If this assumption holds, GNNs outperform flat models. If neighbors carry no signal (e.g., random edges), a GNN reduces to a noisy MLP. Always validate that graph structure improves over a node-features-only baseline before committing to a GNN.
\end{keyinsight}

\section{Key Architectures}
\label{sec:gnn_architectures}
%==============================================================================

\subsection{The Message Passing Framework}

Every major GNN architecture follows the same template. Understanding this template is more important than memorizing individual variants.

\begin{mathresult}{Message Passing Neural Network (MPNN)}
For each node $v$, at layer $l$:
\begin{equation}
\vh_v^{(l)} = \text{UPDATE}\!\left(\vh_v^{(l-1)},\; \text{AGG}\!\left(\left\{\,\text{MSG}\!\left(\vh_v^{(l-1)}, \vh_u^{(l-1)}, e_{vu}\right) : u \in \mathcal{N}(v)\,\right\}\right)\right)
\label{eq:mpnn}
\end{equation}
where $\mathcal{N}(v)$ is the neighbor set of $v$, and $\vh_v^{(0)} = \vx_v$ (input features).
\end{mathresult}

Three design choices define each architecture:
\begin{enumerate}
    \item \textbf{MSG} --- how to compute the message from each neighbor
    \item \textbf{AGG} --- how to aggregate messages (sum, mean, max, attention-weighted)
    \item \textbf{UPDATE} --- how to combine the aggregated message with the node's own representation
\end{enumerate}

The number of message passing layers $L$ determines how far information propagates: after $L$ layers, each node's representation incorporates information from its $L$-hop neighborhood. This is the GNN analogue of receptive field in CNNs.

\subsection{GCN: Graph Convolutional Network}

\textbf{What it is.} The foundational GNN architecture (Kipf and Welling, 2017). Uses a symmetric normalized aggregation that averages neighbor features, weighted by degree.

\begin{mathresult}{GCN Layer}
\begin{equation}
\vh_v^{(l)} = \sigma\!\left(\mW^{(l)} \cdot \text{MEAN}\!\left(\left\{\,\frac{\vh_u^{(l-1)}}{\sqrt{|\mathcal{N}(v)| \cdot |\mathcal{N}(u)|}} : u \in \mathcal{N}(v) \cup \{v\}\,\right\}\right)\right)
\label{eq:gcn}
\end{equation}
where $\sigma$ is a nonlinearity (ReLU), and the self-loop ($v \in \mathcal{N}(v)$) ensures the node retains its own information.
\end{mathresult}

\textbf{When to use.} Good default for homogeneous graphs with moderate size. Simple, fast, well-understood.

\textbf{Pitfalls.} Requires the full adjacency matrix at training time (transductive by default---cannot handle unseen nodes without retraining). The symmetric normalization treats all neighbors equally, which limits expressivity.

\subsection{GraphSAGE}

\textbf{What it is.} SAmple and aggreGatE (Hamilton et al., 2017). Designed for \textit{inductive} learning on large graphs. Two key differences from GCN: (1) samples a fixed-size neighborhood instead of using all neighbors, enabling mini-batch training; (2) separates the node's own features from the aggregated neighbor features with a concatenation.

\textbf{How it works:}
\begin{enumerate}
    \item Sample $k$ neighbors per node at each layer (e.g., $k_1 = 25$, $k_2 = 10$ for two layers)
    \item Aggregate sampled neighbor features (mean, LSTM, or max pooling)
    \item Concatenate the node's own embedding with the aggregation, then apply a linear transform
\end{enumerate}

\textbf{When to use.} Large graphs (millions to billions of nodes) where full-batch GCN is infeasible. Production systems where new nodes appear over time (inductive setting).

\textbf{Pitfalls.} Neighbor sampling introduces variance. The sampling budget creates a trade-off: larger samples are more accurate but increase the computation tree exponentially (with $L$ layers and $k$ samples per layer, the computation tree has $O(k^L)$ nodes).

\subsection{GAT: Graph Attention Network}

\textbf{What it is.} Applies attention over neighbors to learn \textit{which} neighbors matter most (Velickovic et al., 2018). Instead of treating all neighbors equally (GCN) or sampling uniformly (GraphSAGE), GAT computes a learned attention weight for each edge.

\begin{mathresult}{GAT Attention}
\begin{equation}
\alpha_{vu} = \frac{\exp\!\left(\text{LeakyReLU}\!\left(\va^T [\mW\vh_v \,\|\, \mW\vh_u]\right)\right)}{\sum_{w \in \mathcal{N}(v)} \exp\!\left(\text{LeakyReLU}\!\left(\va^T [\mW\vh_v \,\|\, \mW\vh_w]\right)\right)}
\label{eq:gat}
\end{equation}
where $\|$ is concatenation, $\va$ is a learnable attention vector, and $\mW$ projects node features.
\end{mathresult}

GAT uses multi-head attention (same concept as in Transformers): $H$ independent attention heads, with outputs concatenated (intermediate layers) or averaged (final layer).

\textbf{When to use.} Heterogeneous neighborhoods where neighbor importance varies significantly. Works well when different neighbors contribute different types of information.

\textbf{Pitfalls.} The attention mechanism in GATv1 is a function of individual node features, not their \textit{interaction}---it can rank neighbors the same way regardless of the target node. GATv2 (Brody et al., 2022) fixes this by applying the nonlinearity after concatenation, enabling truly dynamic attention. Attention also adds compute and memory cost per edge.

\subsection{GIN and the Weisfeiler-Leman Connection}

\textbf{What it is.} The Graph Isomorphism Network (Xu et al., 2019) is designed to be \textit{maximally expressive} among message-passing GNNs. Its aggregation uses sum (not mean or max), which preserves multiset structure and makes the layer update injective.

\textbf{Why it matters (the WL test intuition).} The Weisfeiler-Leman (WL) graph isomorphism test is a classical algorithm that iteratively refines node labels by hashing each node's label together with the \textit{multiset} of its neighbors' labels. Xu et al.\ proved that message-passing GNNs are \textit{at most} as powerful as the 1-WL test at distinguishing non-isomorphic graphs. GIN achieves this upper bound; GCN and GraphSAGE (which use mean aggregation) do not---they cannot distinguish certain graph structures that sum aggregation can.

\textbf{Concrete example.} Mean aggregation cannot distinguish a node with two neighbors of feature $[1, 0]$ from a node with one such neighbor---both produce mean $[1, 0]$. Sum aggregation produces $[2, 0]$ vs.\ $[1, 0]$, preserving the count.

\textbf{When to use.} Graph classification tasks where structural discrimination matters (molecular property prediction, graph-level anomaly detection).

\textbf{Pitfalls.} Being theoretically most expressive does not always mean best performance. On node classification with noisy features, the additional expressivity can lead to overfitting. GIN's advantage is most visible on small graph classification benchmarks.

\begin{warningbox}
All standard message-passing GNNs are bounded by the 1-WL test. They cannot distinguish certain non-isomorphic graphs (e.g., specific regular graphs with the same degree sequence). If your task requires distinguishing such structures, you need higher-order GNNs, subgraph methods, or positional/structural encodings. This is a common interview follow-up: ``What are the theoretical limitations of message passing?''
\end{warningbox}

\section{Challenges}
\label{sec:gnn_challenges}
%==============================================================================

\subsection{Over-Smoothing}

\textbf{What it is.} As you stack more GNN layers, node representations converge to indistinguishable values. After $L$ layers of message passing, each node's representation is a weighted average of its $L$-hop neighborhood. For dense graphs, a few layers suffice to cover the entire graph, causing all node representations to collapse to a near-identical vector. This is the GNN equivalent of vanishing gradients---but worse, because it is a fundamental property of the aggregation, not just a training issue.

\textbf{Why it happens.} Message passing is a form of Laplacian smoothing. Each layer averages a node's features with its neighbors, which is equivalent to applying a low-pass filter on the graph. Repeated application of a low-pass filter kills all high-frequency (local, discriminative) signal, leaving only the graph's leading eigenvector.

\begin{keyinsight}{Over-Smoothing Limits GNN Depth in Practice}
Most GNNs work best with 2--3 layers. Beyond that, performance typically degrades. This is not because deeper GNNs cannot be trained (they can) but because the representations lose discriminative power. A 2-layer GNN covers the 2-hop neighborhood, which is sufficient for most tasks. Deeper GNNs are needed only when the task genuinely requires long-range graph dependencies---and in that case, you need explicit anti-smoothing mechanisms.
\end{keyinsight}

\begin{table}[H]
\centering
\caption{Over-smoothing solutions}
\begin{tabularx}{\textwidth}{lXX}
\toprule
\textbf{Solution} & \textbf{How It Works} & \textbf{Trade-off} \\
\midrule
Residual connections & Skip connections between GNN layers: $\vh^{(l)} = \vh^{(l-1)} + \text{GNN}(\vh^{(l-1)})$ & Simple; partially mitigates but does not fully solve \\
JKNet (Jumping Knowledge) & Concatenate or max-pool representations from all layers as final embedding & Increases output dimension; adds layer-selection mechanism \\
DropEdge & Randomly remove edges during training (analogous to dropout for graphs) & Reduces over-smoothing by limiting propagation; adds noise \\
PairNorm & Normalize node embeddings to maintain constant total pairwise distance & Prevents collapse; may reduce expressivity \\
Graph Transformer & Replace local message passing with global attention over all nodes & Avoids locality constraint; quadratic cost in $|V|$ \\
Subgraph sampling & Extract local subgraphs and process independently & Limits propagation depth; loses global context \\
\bottomrule
\end{tabularx}
\end{table}

\textbf{The practical rule.} Start with 2 layers. If the task needs longer-range information, add layers one at a time with residual connections and monitor node embedding similarity (e.g., mean cosine similarity between representations). If similarity approaches 1.0, you have over-smoothed.

\subsection{Over-Squashing}

\textbf{What it is.} The complementary problem to over-smoothing. When a node needs information from $L$ hops away, that information must be compressed through a fixed-width bottleneck at each intermediate node. Exponentially many distant nodes' messages get ``squashed'' into a fixed-dimensional vector. This is analogous to the information bottleneck in deep RNNs.

\textbf{Mitigation.} Graph rewiring (add ``shortcut'' edges to reduce diameter), virtual nodes (a global node connected to all others that acts as a broadcast channel), or Graph Transformers (bypass locality entirely with global attention).

\subsection{Scalability}

Real-world graphs have billions of nodes and edges. Full-batch training is impossible.

\begin{table}[H]
\centering
\caption{GNN scalability techniques}
\begin{tabularx}{\textwidth}{lXXX}
\toprule
\textbf{Method} & \textbf{How It Works} & \textbf{Pro} & \textbf{Con} \\
\midrule
Neighbor sampling (GraphSAGE) & Sample $k$ neighbors per node per layer & Inductive, simple & Exponential fan-out with depth \\
Cluster-GCN & Partition graph into clusters, train on subgraphs & Reduces fan-out & Inter-cluster edges lost per batch \\
GraphSAINT & Sample subgraphs with importance sampling & Unbiased gradient estimates & Complex sampling scheme \\
Mini-batch with historical embeddings & Cache neighbor embeddings from prior iterations & Reduces recomputation & Stale embeddings add noise \\
\bottomrule
\end{tabularx}
\end{table}

\textbf{Neighbor sampling fan-out math.} For a 2-layer GNN with fan-out $[25, 10]$, computing one target node's embedding requires sampling $25 \times 10 = 250$ second-hop nodes plus 25 first-hop nodes $= 275$ total. For a batch of 1024 target nodes, you process up to $1024 \times 275 \approx 280$K node features per batch. This is manageable but grows quickly with more layers or larger fan-out.

\textbf{Cluster-GCN} (Chiang et al., 2019) avoids the fan-out problem entirely by partitioning the graph (e.g., using METIS) and training on entire subgraphs. Within a subgraph, full-batch message passing is used. The cost: edges between clusters are dropped during training, introducing bias. Mixing clusters across mini-batches partially mitigates this.

\begin{warningbox}
The exponential fan-out problem in neighbor sampling means that a 3-layer GNN with fan-out $[25, 10, 10]$ touches $25 \times 10 \times 10 = 2{,}500$ nodes per target node. This limits practical GNN depth even when over-smoothing is not a concern. If your interviewer asks ``why not just add more layers to capture longer-range dependencies?'' the answer is both over-smoothing \textit{and} the computational cost of deep neighbor sampling.
\end{warningbox}

\section{Applications}
\label{sec:gnn_applications}
%==============================================================================

\subsection{Social Networks}

\textbf{Tasks:} Community detection, influence prediction, friend recommendation, content recommendation.

\textbf{Why GNNs help.} Social networks exhibit strong homophily (friends share interests) and structural roles (influencers have distinct neighborhoods). GNNs capture both through message passing. For friend recommendation, link prediction with GNN-generated embeddings outperforms collaborative filtering on cold-start users because the graph structure provides signal even without interaction history.

\textbf{Scale challenge.} Social graphs are among the largest (billions of nodes). Production systems at Meta use GraphSAGE-style sampling with feature caching and distributed training.

\subsection{Molecular Property Prediction}

\textbf{Tasks:} Predict solubility, toxicity, binding affinity, or other physicochemical properties from molecular structure.

\textbf{Why GNNs are natural.} A molecule is literally a graph: atoms are nodes, bonds are edges. Both node features (atom type, charge, hybridization) and edge features (bond type, stereochemistry) carry signal. Graph-level prediction (pooling all node embeddings into a single graph embedding) is the standard approach.

\textbf{Architecture choice.} GIN or SchNet (which incorporates 3D coordinates as continuous edge features) are common. Attention-based variants (e.g., GPS---General Powerful Scalable graph transformer) that combine message passing with global attention are state-of-the-art on benchmarks like OGB-LSC.

\textbf{Practical note.} Molecular graphs are small (typically 10--100 nodes), so scalability is not a concern. The challenge is data efficiency---labeled molecular data is expensive to obtain (wet lab experiments), making few-shot learning and pretraining (e.g., self-supervised on unlabeled molecules) important.

\subsection{Fraud Detection}

\textbf{Tasks:} Identify fraudulent accounts, transactions, or reviews in a transaction or interaction graph.

\textbf{Why GNNs help.} Fraudsters create networks of colluding accounts. Individual features (e.g., account age, transaction frequency) can be spoofed, but the graph structure---dense clusters of new accounts transacting with each other in unusual patterns---is much harder to fake. GNNs detect these structural anomalies by propagating neighborhood information.

\textbf{Key design decisions:}
\begin{itemize}
    \item \textbf{Graph construction:} How to define edges (co-transaction, shared device, shared IP, shared payment method). Multiple edge types create a heterogeneous graph.
    \item \textbf{Label scarcity:} Fraud labels are rare ($<$1\% positive rate). Combine GNN with oversampling, focal loss, or semi-supervised approaches.
    \item \textbf{Temporal dynamics:} Fraud patterns evolve. Use temporal edges and retrain frequently, or use dynamic GNNs that model edge timestamps.
    \item \textbf{Adversarial robustness:} Fraudsters adapt. The model must be robust to adversarial graph manipulation (e.g., creating benign-looking edges to evade detection).
\end{itemize}

\subsection{Knowledge Graphs}

\textbf{Tasks:} Link prediction (knowledge base completion), entity classification, relation extraction.

\textbf{Representation.} Knowledge graphs store facts as (head, relation, tail) triples, e.g., (Einstein, born\_in, Germany). The graph is directed and multi-relational.

\textbf{Approaches:}
\begin{itemize}
    \item \textbf{Embedding methods} (TransE, RotatE, ComplEx): Learn entity and relation embeddings such that $\vh + \mathbf{r} \approx \mathbf{t}$ for valid triples. Simple, scalable, but do not use node features.
    \item \textbf{GNN-based} (R-GCN, CompGCN): Apply message passing with relation-specific transformations. Each relation type has its own weight matrix (or a basis decomposition to keep parameters manageable). These methods can incorporate node features and multi-hop reasoning.
\end{itemize}

\textbf{Practical note.} Knowledge graphs in industry (Google Knowledge Graph, Wikidata) have billions of triples. Embedding methods dominate at scale due to simplicity. GNN-based methods are preferred when node features are available or multi-hop reasoning is needed.

%--- Question 1: Architecture Design - Fraud detection system ---
\begin{interviewq}
\textbf{Q: Design a GNN-based system for real-time fraud detection on a financial transaction graph.}

\textbf{Difficulty:} L6 \quad \textbf{Type:} Architecture Design \quad \textbf{Frequency:} \freqmed{}

\textbf{Strong answer:}

\textbf{Step 1: Problem formulation.} Binary node classification: label each account as fraudulent or legitimate. The key insight is that fraud is a \textit{network} phenomenon---fraudulent accounts cluster together and exhibit unusual connectivity patterns that are invisible to per-account feature models.

\textbf{Step 2: Graph construction.} Build a heterogeneous multi-relational graph. Nodes: user accounts, devices, IP addresses, payment instruments. Edges: user-device (login), user-IP (session), user-payment (owns), user-user (transaction), user-user (shared device within 24h). Edge types are critical---shared-device edges between unrelated accounts are the strongest fraud signal.

\textbf{Step 3: Model.} Two-layer R-GCN (relational GCN) with relation-specific weight matrices (using basis decomposition to reduce parameters). Use GraphSAGE-style neighbor sampling for scalability (sample 15 neighbors per edge type per layer). Output: per-node fraud probability via sigmoid on the final embedding.

\textbf{Step 4: Handling class imbalance.} Fraud rate is typically 0.1--1\%. Use focal loss ($\gamma = 2$) or weighted binary cross-entropy with upweight on positives. Optimize for precision at fixed recall (e.g., 90\% recall) rather than accuracy or AUC alone, since false positives have a direct user-experience cost.

\textbf{Step 5: Serving.} Fraud detection is real-time. Precompute node embeddings periodically (e.g., hourly) and cache them. For a new transaction, look up sender and receiver embeddings, concatenate with transaction features, and run through a lightweight MLP classifier. Retrain the GNN daily on the most recent labeled data, including investigator-confirmed fraud labels with a 24--48h feedback delay.

\textbf{Step 6: Monitoring.} Track precision@90\%-recall over time. Monitor graph statistics (average degree, new edge rate) for distribution shift. A sudden spike in new accounts creating dense subgraphs is itself a fraud signal worth alerting on.

\textbf{Red flags} (what NOT to say):
\begin{itemize}
    \item ``Just use a GNN on all the data''---without explaining graph construction choices, edge types, and why relational structure matters for fraud specifically.
    \item Ignoring the real-time serving constraint---proposing full GNN inference at transaction time is infeasible at scale; you need precomputed embeddings.
    \item Forgetting adversarial adaptation---fraudsters evolve their behavior. A static model decays.
\end{itemize}

\textbf{What the interviewer is testing:} Can you design a complete ML system (not just pick a model)? Do you understand why GNNs specifically add value here (structural signal that per-account features miss)? Do you handle the practical challenges: class imbalance, real-time serving, temporal dynamics, and adversarial adaptation?

\textbf{What separates good from great:}
\begin{itemize}
    \item \textbf{L5:} Proposes a GNN for fraud detection and mentions class imbalance. Understands that graph structure helps detect fraud rings.
    \item \textbf{L6:} Designs the full pipeline from graph construction through serving. Specifies heterogeneous edge types, embedding caching for real-time inference, and temporal retraining strategy. Handles A/B testing challenges (fraud is a network effect---cannot split users independently; use time-based switchbacks).
    \item \textbf{L7:} Addresses adversarial robustness (feature rotation, ensemble with rule-based signals, red-teaming), discusses incremental graph updates for efficiency, proposes fallback for cold-start accounts (node-features-only MLP), and considers regulatory constraints (explainability requirements for fraud decisions).
\end{itemize}

\textbf{Common follow-ups:} ``How do you handle adversarial adaptation?'' ``What if GNN training is too slow for hourly updates?'' ``How do you handle cold-start accounts with no edges?'' ``How would you A/B test this system?''
\end{interviewq}

%--- Question 2: Trade-off - GNN vs tabular ---
\begin{interviewq}
\textbf{Q: When should you NOT use a GNN? Give examples where simpler approaches win.}

\textbf{Difficulty:} L6 \quad \textbf{Type:} Trade-off \quad \textbf{Frequency:} \freqmed{}

\textbf{Strong answer:}

The decision depends on whether the relational structure carries predictive signal \textit{beyond} what engineered features can capture. GNNs are often overkill, and recognizing when to avoid them is a sign of engineering maturity.

\textbf{Simpler approaches win when:}
\begin{itemize}
    \item \textbf{Hand-crafted graph features suffice.} Degree, PageRank, clustering coefficient, and triangle count fed into XGBoost are often competitive with a GNN---and orders of magnitude simpler to deploy, debug, and maintain.
    \item \textbf{The graph is sparse or disconnected.} If most nodes have fewer than 2 edges, there is minimal neighborhood information for a GNN to leverage. A tabular model on node features will match or beat it.
    \item \textbf{Node features dominate.} If individual features are already highly predictive (e.g., user demographics for churn prediction with weak social signal), the marginal gain from graph structure rarely justifies the infrastructure cost.
    \item \textbf{The ``graph'' is a sequence or grid in disguise.} Text, images, and time series have graph representations, but CNNs, transformers, and RNNs exploit their regular structure far more efficiently.
    \item \textbf{Deployment constraints demand simplicity.} GNNs require graph storage, neighbor sampling infrastructure, and embedding caching. Tabular models need none of this.
\end{itemize}

\textbf{Concrete examples where GNNs lose:}
\begin{enumerate}
    \item \textbf{User churn prediction} where social connections are weak---XGBoost on usage features wins.
    \item \textbf{Product categorization} from text descriptions---a fine-tuned text encoder outperforms any product co-purchase graph GNN.
    \item \textbf{Time series forecasting} where temporal structure matters more than cross-series relationships---LSTMs or temporal transformers beat graph approaches.
\end{enumerate}

\textbf{The pragmatic approach:} Start with a tabular model on node features + hand-crafted graph statistics. Add a 2-layer GCN and compare. If the GNN improves by $>$2\% on the target metric, the structural signal is real. If not, keep the tabular model---the engineering cost of GNNs is only justified when the accuracy gain is substantial.

\textbf{Red flags} (what NOT to say):
\begin{itemize}
    \item ``GNNs are always better when you have a graph''---this shows lack of practical experience. Many graph datasets see no improvement from GNNs over feature-engineered baselines.
    \item ``I would always try a GNN first since it can learn from structure''---this ignores the engineering cost and is the opposite of the simplicity-first principle interviewers look for.
\end{itemize}

\textbf{What the interviewer is testing:} Engineering maturity---do you default to the simplest approach and add complexity only when justified? Can you articulate the specific conditions under which graph structure adds (or does not add) signal?

\textbf{What separates good from great:}
\begin{itemize}
    \item \textbf{L5:} Recognizes that GNNs are not always needed and can list situations where tabular models win. Mentions the importance of baselines.
    \item \textbf{L6:} Provides a concrete decision framework with quantitative thresholds. Gives specific examples of GNN failure cases. Understands the infrastructure overhead of GNNs (graph construction, neighbor sampling, serving).
    \item \textbf{L7:} Discusses the interaction between homophily strength and GNN benefit. Knows that label propagation is a strong diagnostic---if it does not beat a features-only baseline, a GNN is unlikely to help. Can reason about when node2vec embeddings as tabular features are a simpler alternative to full GNN training.
\end{itemize}

\textbf{Common follow-ups:} ``How would you create graph features for the tabular baseline?'' ``What if the tabular model already has graph features---can a GNN still help?'' ``How do you measure whether the graph structure carries signal?''
\end{interviewq}

%--- Question 3: Debugging - Over-smoothing ---
\begin{interviewq}
\textbf{Q: Your GNN's performance degrades as you add more layers. What's happening and how do you fix it?}

\textbf{Difficulty:} L5 \quad \textbf{Type:} Debugging \quad \textbf{Frequency:} \freqmed{}

\textbf{Strong answer:}

The most likely cause is \textbf{over-smoothing}: as you stack more GNN layers, node representations converge to indistinguishable values. This is the GNN equivalent of ``everything looks the same''---and it is not a training bug but a fundamental property of message-passing aggregation.

\textbf{Why it happens.} Each GNN layer aggregates information from a node's neighbors, which is mathematically equivalent to applying a low-pass filter on the graph signal. After $L$ layers, each node's representation is a weighted combination of features from its entire $L$-hop neighborhood. For dense graphs with small diameter (most real-world graphs have diameter $<$10), even 3--4 layers suffice to cover the entire graph. All nodes converge toward the graph's mean feature vector, scaled by the leading eigenvector of the normalized adjacency matrix.

\textbf{Diagnosing it.} Track the mean pairwise cosine similarity of node embeddings across layers. In a healthy GNN (2 layers), this stays below 0.5. At 8+ layers on a dense graph, it approaches 1.0. If adding layers monotonically increases this metric, over-smoothing is confirmed.

\textbf{A secondary cause is over-squashing:} when long-range information must pass through fixed-width bottlenecks at intermediate nodes, messages from exponentially many distant nodes get compressed into a fixed-dimensional vector, losing information. Over-smoothing kills discrimination; over-squashing kills long-range signal.

\textbf{Fixes, in order of practicality:}
\begin{enumerate}
    \item \textbf{Keep it shallow (2--3 layers).} Most tasks do not need $>$3 hops of information.
    \item \textbf{Residual connections:} $\vh^{(l)} = \vh^{(l-1)} + \text{GNN}(\vh^{(l-1)})$. Preserves original signal at each layer.
    \item \textbf{Jumping Knowledge Networks:} Concatenate representations from all layers $[\vh^{(1)} \| \cdots \| \vh^{(L)}]$ and learn which layer matters most per node via attention or max-pooling.
    \item \textbf{DropEdge:} Randomly remove edges during training, slowing information propagation.
    \item \textbf{PairNorm:} Normalize embeddings to maintain constant total pairwise distance.
    \item \textbf{Graph Transformers:} Replace local message passing with global attention to bypass the locality constraint entirely ($O(|V|^2)$ cost, feasible for smaller graphs).
\end{enumerate}

\textbf{The deeper issue.} Over-smoothing is a symptom of a fundamental limitation: message-passing GNNs are bounded by the 1-WL test, and depth does not overcome this---it only makes it worse by destroying local signal. For tasks requiring global graph-level reasoning, the solution is architectural changes: positional encodings, virtual nodes, or Graph Transformers.

\textbf{Red flags} (what NOT to say):
\begin{itemize}
    \item ``It's vanishing gradients---use better initialization or batch norm.'' Over-smoothing is a \textit{representation} issue, not a gradient issue. You can train a 10-layer GNN without gradient problems and still observe over-smoothing.
    \item ``Just use batch normalization''---standard batch norm normalizes per feature, not per node pair. PairNorm is the GNN-specific solution.
    \item ``Add more layers to capture longer-range dependencies''---this is exactly the wrong direction; it worsens over-smoothing.
\end{itemize}

\textbf{What the interviewer is testing:} Do you understand over-smoothing at a mechanistic level (Laplacian smoothing, low-pass filter), not just as a buzzword? Can you propose multiple solutions and explain their trade-offs? Do you know the practical implication (most GNNs should be 2--3 layers)?

\textbf{What separates good from great:}
\begin{itemize}
    \item \textbf{L5:} Correctly identifies over-smoothing as the cause, explains it as neighbor averaging causing convergence, and proposes keeping models shallow with residual connections.
    \item \textbf{L6:} Distinguishes over-smoothing from over-squashing and vanishing gradients. Proposes multiple mitigation strategies with trade-offs. Knows to monitor embedding similarity as a diagnostic.
    \item \textbf{L7:} Connects over-smoothing to spectral graph theory (low-pass filtering, leading eigenvector convergence). Discusses the 1-WL expressivity bound and why depth cannot overcome it. Proposes Graph Transformers or subgraph methods for tasks genuinely requiring long-range information.
\end{itemize}

\textbf{Common follow-ups:} ``What is over-squashing and how does it relate?'' ``Would batch normalization help?'' ``How is this different from vanishing gradients in deep networks?'' ``When would you actually need more than 3 layers?''
\end{interviewq}

%--- Question 4: Trade-off - GCN vs GraphSAGE vs GAT ---
\begin{interviewq}
\textbf{Q: GCN vs GraphSAGE vs GAT---when would you use each?}

\textbf{Difficulty:} L5 \quad \textbf{Type:} Trade-off \quad \textbf{Frequency:} \freqmed{}

\textbf{Strong answer:}

All three follow the message-passing framework but make different design choices for aggregation, and these choices have direct practical consequences.

\textbf{GCN} (Kipf and Welling, 2017) uses a symmetric degree-normalized mean aggregation. All neighbors contribute equally, weighted only by their degree. It is \textit{transductive} by default---requires the full adjacency matrix at training time and cannot directly handle unseen nodes without retraining.
\begin{itemize}
    \item \textbf{Use when:} You have a moderately sized, static graph where all nodes are known at training time. Good default for homogeneous graphs. Simple and fast.
    \item \textbf{Avoid when:} New nodes appear at inference time, the graph is very large, or you need to differentiate neighbor importance.
\end{itemize}

\textbf{GraphSAGE} (Hamilton et al., 2017) samples a fixed-size neighborhood per node and concatenates the node's own features with the aggregated neighbor features. This makes it \textit{inductive} (handles unseen nodes) and enables mini-batch training on large graphs.
\begin{itemize}
    \item \textbf{Use when:} The graph has millions+ nodes, new nodes appear over time (production systems), or you need scalable mini-batch training.
    \item \textbf{Avoid when:} Neighbor importance varies significantly (uniform sampling ignores this). The exponential fan-out with depth (fan-out $[25, 10]$ means 275 nodes per target) limits practical depth.
\end{itemize}

\textbf{GAT} (Velickovic et al., 2018) computes learned attention weights over edges, allowing the model to learn which neighbors matter most. Multi-head attention (like transformers) is standard.
\begin{itemize}
    \item \textbf{Use when:} Neighborhoods are heterogeneous---different neighbors carry different types of signal. Especially useful for heterogeneous graphs and tasks where neighbor relevance varies by context.
    \item \textbf{Avoid when:} Compute budget is tight (attention adds per-edge cost) or the graph is too large for the attention overhead. Note: GATv1 has a subtle limitation---its attention is a function of individual features, not their interaction. GATv2 (Brody et al., 2022) fixes this with truly dynamic attention.
\end{itemize}

\textbf{Decision framework:}
\begin{enumerate}
    \item Static, small-to-medium graph, all nodes known $\to$ GCN
    \item Large or evolving graph, production system $\to$ GraphSAGE
    \item Heterogeneous neighborhoods, neighbor importance varies $\to$ GAT
    \item Need maximum expressivity on small graph classification $\to$ GIN (sum aggregation, WL-equivalent)
\end{enumerate}

\textbf{Red flags} (what NOT to say):
\begin{itemize}
    \item ``GAT is always better because it has attention''---attention adds cost and complexity. On homogeneous graphs where all neighbors are equally informative, GCN often matches GAT at lower cost.
    \item Confusing transductive (GCN) with inductive (GraphSAGE) and not knowing the practical implications for production systems.
    \item ``Just use the one with the best benchmark numbers''---the right choice depends on graph size, whether nodes are static or dynamic, and deployment constraints.
\end{itemize}

\textbf{What the interviewer is testing:} Do you understand the aggregation differences at a mechanical level (mean vs.\ sampled vs.\ attention-weighted)? Can you map each architecture to its ideal use case based on practical constraints, not just benchmark accuracy?

\textbf{What separates good from great:}
\begin{itemize}
    \item \textbf{L5:} Correctly describes all three architectures and gives reasonable guidance on when to use each. Knows GCN is transductive and GraphSAGE is inductive.
    \item \textbf{L6:} Discusses the fan-out problem in GraphSAGE, the GATv1 vs.\ GATv2 attention limitation, and GIN's connection to the WL test. Provides a concrete decision framework based on graph properties.
    \item \textbf{L7:} Connects the aggregation function choice to expressivity theory (sum is injective, mean and max are not). Discusses scalability solutions (Cluster-GCN, GraphSAINT) that allow GCN-style training at GraphSAGE scale. Knows when a Graph Transformer bypasses the limitations of all three.
\end{itemize}

\textbf{Common follow-ups:} ``What is the GATv1 vs.\ GATv2 difference?'' ``How does GIN relate to the Weisfeiler-Leman test?'' ``What about Graph Transformers---do they make these architectures obsolete?'' ``How do you scale GAT to large graphs?''
\end{interviewq}

%--- Question 5: Estimation - GCN memory on 10M nodes ---
\begin{interviewq}
\textbf{Q: Estimate the memory requirements for running a 3-layer GCN on a graph with 10M nodes.}

\textbf{Difficulty:} L6 \quad \textbf{Type:} Estimation \quad \textbf{Frequency:} \freqlow{}

\textbf{Strong answer:}

Let me work through the key memory components with reasonable assumptions.

\textbf{Assumptions:} 10M nodes, average degree 50 (so $\sim$250M directed edges), node feature dimension $d = 128$, hidden dimension $h = 256$, 3 GCN layers, FP32 precision.

\textbf{1. Node feature storage:}
$10\text{M} \times 128 \times 4\text{B} = 5.1\text{ GB}$

\textbf{2. Adjacency structure (edge list):}
$250\text{M edges} \times 2 \times 4\text{B (int32)} = 2.0\text{ GB}$ (source-target pairs).
In sparse CSR format, this is similar: row pointer array ($10\text{M} \times 4\text{B} = 40\text{ MB}$) + column indices ($250\text{M} \times 4\text{B} = 1.0\text{ GB}$).

\textbf{3. Model parameters:}
Layer 1: $128 \times 256 = 32\text{K params}$. Layers 2--3: $256 \times 256 = 65\text{K each}$. Total $\approx 162\text{K params} \times 4\text{B} \approx 0.6\text{ MB}$. \textit{Negligible.}

\textbf{4. Intermediate activations (for training):}
Each layer produces embeddings for all nodes: $10\text{M} \times 256 \times 4\text{B} = 10.2\text{ GB per layer}$. For 3 layers with backprop, you store all intermediate activations: $\sim$30 GB.

\textbf{5. Optimizer states (Adam):}
Two momentum buffers per parameter: $2 \times 162\text{K} \times 4\text{B} \approx 1.3\text{ MB}$. \textit{Negligible} (parameters are tiny in GNNs; the cost is in activations and graph storage).

\textbf{Total estimate:}
\begin{itemize}
    \item \textbf{Inference:} Features (5 GB) + graph (2 GB) + activations (10 GB for one layer) $\approx$ \textbf{17 GB}
    \item \textbf{Full-batch training:} Features (5 GB) + graph (2 GB) + all activations (30 GB) + gradients (30 GB) $\approx$ \textbf{67 GB}---does not fit on a single 80 GB A100 with margin.
\end{itemize}

\textbf{Why full-batch is infeasible and what to do:}
Full-batch training on 10M nodes is impractical. Use GraphSAGE-style neighbor sampling (batch of 1024 target nodes, fan-out $[25, 10, 10]$) to reduce per-batch memory to $\sim$1--2 GB, or Cluster-GCN to partition the graph into subgraphs of 10K--100K nodes and process each as a mini-batch.

\textbf{Red flags} (what NOT to say):
\begin{itemize}
    \item Forgetting the activation memory---model parameters are tiny in GNNs; the memory is dominated by node embeddings and graph structure, which is the opposite of LLMs.
    \item ``10M nodes is fine on one GPU''---at FP32 with a 3-layer GCN, full-batch training requires $\sim$67 GB, which is borderline even on an A100.
    \item Not distinguishing inference memory (forward pass only) from training memory (store all activations for backprop).
\end{itemize}

\textbf{What the interviewer is testing:} Can you perform structured back-of-envelope estimation? Do you understand that GNN memory is dominated by graph structure and node embeddings (not model parameters), which is the key difference from standard deep learning models?

\textbf{What separates good from great:}
\begin{itemize}
    \item \textbf{L5:} Identifies the main memory components (features, graph, activations) and arrives at a reasonable total. Knows full-batch training on 10M nodes is problematic.
    \item \textbf{L6:} Distinguishes training vs.\ inference memory clearly. Quantifies each component and identifies activations as the dominant cost. Proposes neighbor sampling or graph partitioning as solutions and can estimate the per-batch memory for sampled training.
    \item \textbf{L7:} Discusses memory optimization strategies: gradient checkpointing (recompute activations instead of storing), mixed-precision training (halves activation memory), historical embedding caching (trade staleness for memory). Compares memory profiles across GNN variants (GAT has per-edge attention weights adding memory; GIN is similar to GCN).
\end{itemize}

\textbf{Common follow-ups:} ``How does the memory change if you use FP16?'' ``What if average degree is 500 instead of 50?'' ``How does neighbor sampling change the memory profile?'' ``Compare GNN memory to transformer memory---what dominates in each?''
\end{interviewq}

%--- Question 6: Trade-off - GCN vs GraphSAGE vs GAT (from old Q2, refocused) ---
\begin{interviewq}
\textbf{Q: GCN vs GraphSAGE vs GAT---which would you choose for a production recommendation system at scale?}

\textbf{Difficulty:} L6 \quad \textbf{Type:} Trade-off \quad \textbf{Frequency:} \freqmed{}

\textbf{Strong answer:}

For a production recommendation system at scale (billions of user-item interactions, millions of new items daily), the answer is almost always \textbf{GraphSAGE or a GraphSAGE-style architecture} (e.g., PinSage). Here is why, by elimination:

\textbf{GCN is ruled out} because it is transductive---it requires the full adjacency matrix at training time and cannot handle unseen nodes without retraining. In a recommendation system, new users and items appear constantly. Retraining the entire model for every new node is infeasible.

\textbf{GAT is problematic at scale} because attention computes a per-edge weight, which means $O(|E|)$ attention computations per forward pass. On a graph with billions of edges, this is expensive. Additionally, GAT's attention benefit (learning neighbor importance) is less critical for recommendations where collaborative filtering signal is relatively uniform---a user's past interactions are all roughly equally informative.

\textbf{GraphSAGE wins because:}
\begin{itemize}
    \item \textbf{Inductive:} Generates embeddings for new users/items using their neighborhood, without retraining.
    \item \textbf{Scalable:} Mini-batch training with neighbor sampling works at billion-node scale.
    \item \textbf{Production-proven:} PinSage (Pinterest, 2018) demonstrated GraphSAGE at scale with 3B nodes and 18B edges, using importance-based neighbor sampling and MapReduce-based training.
\end{itemize}

\textbf{The production architecture:}
\begin{enumerate}
    \item Train a 2-layer GraphSAGE on the user-item interaction graph (bipartite).
    \item Precompute and cache item embeddings offline. Incrementally update embeddings for items with changed neighborhoods.
    \item At serving time, compute the user embedding from their recent interactions (sample neighbors from the graph), then retrieve nearest-neighbor items from an ANN index (FAISS, ScaNN) over precomputed item embeddings.
    \item Refresh embeddings and retrain on a daily or weekly cadence.
\end{enumerate}

\textbf{Red flags} (what NOT to say):
\begin{itemize}
    \item ``Use GAT because attention is always better''---at recommendation scale, the per-edge attention cost is prohibitive and the benefit is marginal.
    \item ``GCN is fine, just retrain when new items arrive''---this shows no understanding of production constraints at scale.
    \item Ignoring the serving architecture---the model is only half the system; retrieval, caching, and incremental updates matter as much.
\end{itemize}

\textbf{What the interviewer is testing:} Can you reason about architecture selection under production constraints (scale, latency, new-node handling)? Do you understand the full pipeline from training to serving for a recommendation GNN?

\textbf{What separates good from great:}
\begin{itemize}
    \item \textbf{L5:} Correctly identifies GraphSAGE as the right choice for scale and knows it is inductive. Understands that GCN's transductive nature is a dealbreaker.
    \item \textbf{L6:} Describes the full production pipeline (training, embedding caching, ANN retrieval, incremental updates). References PinSage. Quantifies the scalability constraints that rule out GCN and GAT.
    \item \textbf{L7:} Discusses advanced production optimizations: importance-based neighbor sampling (not uniform), curriculum negative sampling, multi-task learning on the same graph (click prediction + engagement), and how to handle the cold-start problem (content-based fallback for zero-edge items). Knows LightGCN (simplified GCN without feature transforms, designed for collaborative filtering).
\end{itemize}

\textbf{Common follow-ups:} ``How do you handle cold-start items with no interactions?'' ``What is PinSage and how does it differ from vanilla GraphSAGE?'' ``How do you keep embeddings fresh as the graph evolves?'' ``Would you use a heterogeneous GNN if you have multiple edge types (click, purchase, save)?''
\end{interviewq}

%--- Question 7: Conceptual - Expressivity and WL test ---
\begin{interviewq}
\textbf{Q: What are the theoretical expressivity limitations of message-passing GNNs, and when do they matter in practice?}

\textbf{Difficulty:} L6 \quad \textbf{Type:} First Principles \quad \textbf{Frequency:} \freqlow{}

\textbf{Strong answer:}

Message-passing GNNs are bounded by the \textbf{1-dimensional Weisfeiler-Leman (1-WL) graph isomorphism test}. This means there exist pairs of non-isomorphic graphs (structurally different) that no message-passing GNN can distinguish, regardless of depth, width, or training.

\textbf{Why this limit exists.} The WL test iteratively refines node labels by hashing each node's label together with the \textit{multiset} of its neighbors' labels. Xu et al.\ (2019) proved that message-passing GNNs are \textit{at most} as powerful as 1-WL at distinguishing graphs. The proof is intuitive: both message passing and WL perform the same operation---aggregate neighbor information and update---so they have the same discriminative power.

\textbf{Which GNNs hit the bound.} GIN (Graph Isomorphism Network) achieves the 1-WL upper bound by using sum aggregation (which is injective on multisets). GCN and GraphSAGE use mean aggregation, which is \textit{not} injective---they cannot even distinguish between a node with two neighbors of feature $[1, 0]$ and a node with one such neighbor (both produce mean $[1, 0]$; sum produces $[2, 0]$ vs.\ $[1, 0]$).

\textbf{When this matters in practice:}
\begin{itemize}
    \item \textbf{Molecular property prediction:} Certain chemical substructures (e.g., cyclopropane vs.\ propane, or specific ring systems) are indistinguishable under 1-WL. This can cause GNNs to predict identical properties for structurally different molecules.
    \item \textbf{Regular graphs:} 1-WL cannot distinguish $k$-regular graphs with the same degree sequence. If your task involves detecting structural roles in regular graphs, standard GNNs fail.
    \item \textbf{Graph classification:} When fine-grained structural discrimination is needed (isomorphism detection, subgraph counting), the 1-WL bound is a real limitation.
\end{itemize}

\textbf{When this does NOT matter:}
\begin{itemize}
    \item \textbf{Node classification with rich features:} If node features are sufficiently discriminative, the structural limitation is masked. Most production GNN use cases (fraud detection, recommendations) fall here.
    \item \textbf{Large, irregular graphs:} The problematic graph pairs for 1-WL are mostly small, highly symmetric structures. Large real-world graphs are rarely symmetry-pathological.
\end{itemize}

\textbf{Going beyond 1-WL:}
\begin{itemize}
    \item \textbf{Higher-order GNNs} ($k$-WL equivalent) that pass messages between $k$-tuples of nodes, not individual nodes. More expressive but $O(n^k)$ complexity.
    \item \textbf{Subgraph methods:} Extract ego-nets or subgraphs around each node and process them independently---breaks symmetry.
    \item \textbf{Positional/structural encodings:} Random walk encodings, Laplacian eigenvectors, or random features added as node features to break symmetry.
    \item \textbf{Graph Transformers with positional encoding:} Global attention bypasses the locality of message passing, and positional encodings provide structural awareness.
\end{itemize}

\textbf{Red flags} (what NOT to say):
\begin{itemize}
    \item ``Just add more layers to increase expressivity''---depth does not overcome the 1-WL bound; it only worsens over-smoothing.
    \item Treating the WL limitation as purely theoretical with no practical relevance---it matters for molecular design and graph-level classification.
    \item Confusing expressivity (what the model \textit{can} represent) with generalization (what it \textit{learns} from data).
\end{itemize}

\textbf{What the interviewer is testing:} Do you understand the theoretical foundations of GNN expressivity? Can you connect formal theory (WL test) to practical implications (which tasks are affected)? This question separates candidates who have read the key papers from those who only know GNNs at an API level.

\textbf{What separates good from great:}
\begin{itemize}
    \item \textbf{L5:} Knows that message-passing GNNs have expressivity limitations and that sum aggregation (GIN) is more expressive than mean (GCN).
    \item \textbf{L6:} Explains the WL test connection, gives concrete examples of indistinguishable graphs, and discusses when the limitation matters practically. Knows about positional encodings and higher-order methods as solutions.
    \item \textbf{L7:} Discusses the hierarchy of $k$-WL tests and their computational costs. Knows about specific methods beyond 1-WL (ESAN, GNN-AK, subgraph GNNs). Can articulate why Graph Transformers with positional encodings are not strictly more powerful than 1-WL without careful design (plain attention is still permutation-equivariant without positional information).
\end{itemize}

\textbf{Common follow-ups:} ``Give an example of two graphs that 1-WL cannot distinguish.'' ``Why does sum aggregation achieve the WL bound but mean does not?'' ``How do Graph Transformers relate to the WL hierarchy?'' ``Is the WL bound tight---are there tasks where it actually hurts performance?''
\end{interviewq}

%--- Question 8: Conceptual/Trade-off - Heterogeneous GNNs ---
\begin{interviewq}
\textbf{Q: How do you handle heterogeneous graphs (multiple node types, multiple edge types) in a GNN?}

\textbf{Difficulty:} L5 \quad \textbf{Type:} Conceptual \quad \textbf{Frequency:} \freqmed{}

\textbf{Strong answer:}

Heterogeneous graphs (e.g., an e-commerce graph with users, items, stores, and brands connected by different relation types) require architectures that can handle multiple node types and edge types, since vanilla GCN/GraphSAGE treat all nodes and edges identically.

\textbf{The core challenge:} Different edge types carry different semantics (a ``purchased'' edge means something fundamentally different from a ``viewed'' edge). Using a single shared weight matrix for all edge types conflates these signals. Different node types live in different feature spaces (user features vs.\ item features), so they cannot share the same input projection.

\textbf{Key approaches:}

\textbf{1. R-GCN (Relational GCN):} Uses relation-specific weight matrices $\mW_r$ for each edge type $r$:
\[
\vh_v^{(l)} = \sigma\!\left(\sum_{r \in \mathcal{R}} \sum_{u \in \mathcal{N}_r(v)} \frac{1}{|\mathcal{N}_r(v)|} \mW_r^{(l)} \vh_u^{(l-1)}\right)
\]
With many relation types, this has too many parameters. Two solutions: \textit{basis decomposition} ($\mW_r = \sum_b a_{rb} \mB_b$, shared bases with relation-specific coefficients) or \textit{block-diagonal decomposition}.

\textbf{2. Heterogeneous Graph Transformer (HGT):} Uses relation-specific attention. Different head groups attend to different edge types, with type-specific query, key, and value projections. More expressive than R-GCN but more expensive.

\textbf{3. Metapath-based methods (HAN):} Define semantically meaningful paths through the heterogeneous graph (e.g., User $\to$ Item $\to$ User for ``users who buy similar items'') and aggregate along these metapaths. Each metapath captures a different type of relationship. Limitation: requires domain expertise to define metapaths.

\textbf{4. Simple pragmatic approach:} Project all node types into a shared embedding space with type-specific linear projections, then apply a standard homogeneous GNN (GraphSAGE, GAT) with edge-type-specific message functions. This is the most common production approach.

\textbf{Decision framework:}
\begin{itemize}
    \item Few edge types ($<$5), need simplicity $\to$ R-GCN with basis decomposition
    \item Many edge types, need flexibility $\to$ HGT or type-specific projections + standard GNN
    \item Clear semantic paths matter $\to$ Metapath-based (HAN)
    \item Production at scale $\to$ Shared embedding space + GraphSAGE with per-type sampling
\end{itemize}

\textbf{Red flags} (what NOT to say):
\begin{itemize}
    \item ``Just treat all edges the same''---this discards the semantic differences between relation types, which is often the most valuable signal.
    \item ``Use a separate GNN for each edge type''---this loses the cross-type interaction that heterogeneous GNNs are designed to capture.
\end{itemize}

\textbf{What the interviewer is testing:} Can you handle real-world graph complexity beyond the simple homogeneous case? Do you understand the parameter explosion problem with relation-specific weights and how to manage it?

\textbf{What separates good from great:}
\begin{itemize}
    \item \textbf{L5:} Knows that heterogeneous graphs need relation-specific processing and can describe R-GCN at a high level. Understands that different node types need different input projections.
    \item \textbf{L6:} Compares R-GCN, HGT, and metapath-based approaches with trade-offs. Knows about basis decomposition to manage parameter count. Can design a heterogeneous GNN for a specific application (e.g., e-commerce, knowledge graphs).
    \item \textbf{L7:} Discusses the connection between metapaths and attention-based methods (attention can implicitly learn metapath importance). Knows about relational message passing in the context of knowledge graph completion (CompGCN). Understands how heterogeneous GNNs interact with scalability---type-specific sampling strategies for GraphSAGE on heterogeneous graphs.
\end{itemize}

\textbf{Common follow-ups:} ``How does R-GCN's basis decomposition work?'' ``What are metapaths and why might they be better than learned attention?'' ``How would you build a heterogeneous GNN for a knowledge graph vs.\ an e-commerce graph?'' ``Does PyG or DGL have better support for heterogeneous graphs?''
\end{interviewq}
