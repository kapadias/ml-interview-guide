\chapter{Reinforcement Learning and RLHF}
\label{chap:reinforcement_learning}

\begin{tldr}
Reinforcement learning (RL) has re-entered the mainstream ML engineer's toolkit---not because you will build game-playing agents, but because RLHF is how frontier LLMs are aligned. This chapter covers RL fundamentals (MDPs, policy gradients, PPO) at the depth needed to understand the RLHF pipeline, then walks through each stage: supervised fine-tuning (SFT), reward model training, and PPO-based policy optimization. It covers DPO as the increasingly popular alternative that eliminates the reward model entirely, the failure modes that plague alignment (reward hacking, alignment tax), and newer approaches like Constitutional AI and RLAIF. If you interview for any LLM-adjacent role at Staff+ level, you must be able to whiteboard the RLHF pipeline and articulate the tradeoffs between PPO and DPO.
\end{tldr}

\section{RL Fundamentals for LLM Engineers}
\label{sec:rl_fundamentals}
%==============================================================================

You do not need to be an RL researcher to pass an ML interview. But you do need enough RL fluency to explain why PPO is used in RLHF, what a reward model does, and why the KL penalty exists. This section covers exactly that---nothing more, nothing less.

\subsection{Markov Decision Process (MDP)}

\textbf{What it is.} An MDP formalizes sequential decision-making. An agent observes a state, takes an action, receives a reward, and transitions to a new state. The goal is to find a policy $\pi(a \mid s)$ that maximizes cumulative reward.

\textbf{Components:}
\begin{itemize}
    \item $\mathcal{S}$: State space (for LLMs: the token sequence generated so far)
    \item $\mathcal{A}$: Action space (for LLMs: the vocabulary---choosing the next token)
    \item $P(s' \mid s, a)$: Transition dynamics (for LLMs: deterministic---appending the chosen token)
    \item $R(s, a)$: Reward function (for LLMs: the reward model's score, given only at the end of generation)
    \item $\gamma$: Discount factor (for LLMs: typically $1.0$ since episodes are short)
\end{itemize}

\textbf{Interview angle.} The interviewer is testing whether you can map the abstract MDP framework onto the concrete LLM setting. Always ground your RL answers in the LLM context: ``the action is token selection, the state is the sequence so far, and the reward comes from the reward model at the end of generation.''

\subsection{Value Functions and Policy Gradient}

\textbf{Value vs.\ policy methods.} Two families of RL algorithms exist. Value-based methods (DQN) learn a value function and derive a policy from it. Policy-based methods (REINFORCE, PPO) directly optimize the policy. LLM alignment uses policy-based methods because the action space (vocabulary, 32K--128K tokens) is too large for value-based approaches.

\begin{mathresult}{Policy Gradient Theorem (REINFORCE)}
\begin{equation}
\nabla_\theta J(\theta) = \E_{\tau \sim \pi_\theta}\left[\sum_{t=0}^{T} \nabla_\theta \log \pi_\theta(a_t \mid s_t) \cdot R(\tau)\right]
\end{equation}
\textbf{Intuition:} Increase the probability of actions that led to high reward; decrease it for actions that led to low reward. The gradient pushes the policy toward trajectories $\tau$ with higher return $R(\tau)$.
\end{mathresult}

\textbf{The variance problem.} REINFORCE has extremely high variance because the full trajectory return $R(\tau)$ is used as the credit signal for every action. A single unlucky trajectory can dominate the gradient. Two solutions:

\begin{enumerate}
    \item \textbf{Baseline subtraction:} Replace $R(\tau)$ with the \textit{advantage} $A(s_t, a_t) = Q(s_t, a_t) - V(s_t)$---how much better this action was than average. The value function $V(s_t)$ serves as the baseline.
    \item \textbf{Actor-critic:} Learn both a policy (actor) and a value function (critic) simultaneously. The critic estimates the baseline; the actor uses the advantage to update. PPO is an actor-critic method.
\end{enumerate}

\subsection{PPO (Proximal Policy Optimization)}

\textbf{What it is.} PPO is the workhorse optimizer for RLHF. It is a policy gradient method that prevents destructively large updates by clipping the policy ratio---ensuring each update stays ``close'' to the previous policy.

\begin{mathresult}{PPO Clipped Objective}
\begin{equation}
\loss_{\text{PPO}} = -\E_t\left[\min\!\left(r_t(\theta) \hat{A}_t,\; \text{clip}\!\left(r_t(\theta), 1-\epsilon, 1+\epsilon\right)\hat{A}_t\right)\right]
\end{equation}
where $r_t(\theta) = \frac{\pi_\theta(a_t \mid s_t)}{\pi_{\theta_{\text{old}}}(a_t \mid s_t)}$ is the probability ratio and $\epsilon = 0.2$ is typical.
\end{mathresult}

\textbf{Why clipping?} Without clipping, a large policy update can catastrophically change behavior---the model might go from coherent text to gibberish in one step. The clip prevents $r_t$ from moving too far from $1.0$ in either direction. If the advantage is positive (good action), $r_t$ is capped at $1 + \epsilon$; if negative (bad action), $r_t$ is capped at $1 - \epsilon$.

\textbf{Why PPO for RLHF specifically:}
\begin{itemize}
    \item \textbf{Sample efficiency:} PPO reuses collected trajectories for multiple gradient updates (unlike REINFORCE, which is single-use).
    \item \textbf{Stability:} The clipping mechanism prevents the catastrophic updates that would corrupt a pretrained LLM.
    \item \textbf{Simplicity:} Compared to TRPO (which requires constrained optimization with a KL trust region), PPO achieves similar stability through a simple clamp operation.
\end{itemize}

\subsection{Stage 1: Supervised Fine-Tuning (SFT)}

\textbf{What it is.} Fine-tune the pretrained base model on high-quality (instruction, response) pairs using standard cross-entropy loss. This turns a text-completion model into an instruction-following model.

\textbf{Why it matters.} The base model can generate text, but it does not know it is supposed to \textit{answer questions}. SFT teaches the format---respond to queries, follow instructions, produce structured outputs. Without SFT, the RL stage has no reasonable starting policy to improve.

\textbf{Key design decisions:}
\begin{itemize}
    \item \textbf{Data quality $>$ data quantity.} A few thousand expertly written examples often outperform millions of noisy ones (LIMA showed 1,000 carefully curated examples can produce a strong instruction-following model).
    \item \textbf{Loss masking.} Only compute cross-entropy loss on the response tokens, not the instruction tokens. The model should learn to \textit{generate} good responses, not to predict the prompt.
    \item \textbf{Chat template.} Use consistent formatting (e.g., ChatML, Llama-style \texttt{[INST]...[/INST]}) so the model learns role boundaries.
\end{itemize}

\textbf{Pitfalls.} Over-training on SFT data leads to a verbose, sycophantic model that sounds helpful but does not actually calibrate quality. SFT teaches format, not judgment---that is what the RL stage adds.

\subsection{Stage 2: Reward Model Training}

\textbf{What it is.} Train a separate model to predict which of two responses a human would prefer. Given a prompt $x$ and two candidate responses $y_w$ (preferred) and $y_l$ (dispreferred), the reward model $R_\phi$ should assign a higher scalar score to $y_w$.

\begin{mathresult}{Bradley-Terry Preference Loss}
\begin{equation}
\loss_{\text{RM}} = -\E_{(x, y_w, y_l)}\left[\log \sigma\!\left(R_\phi(x, y_w) - R_\phi(x, y_l)\right)\right]
\end{equation}
This is simply binary cross-entropy on the preference pair, using the score difference as the logit.
\end{mathresult}

\textbf{Architecture.} The reward model is typically initialized from the SFT model with the language modeling head replaced by a scalar output head. It shares the same tokenizer and context window.

\textbf{Data.} Human annotators are shown a prompt and two (or more) model-generated responses. They rank them by preference. Common annotation guidelines cover helpfulness, truthfulness, and safety. Inter-annotator agreement is typically 70--80\%---the task is inherently noisy.

\begin{warningbox}
The reward model is only as good as its training distribution. If the RM was trained on responses from a 7B model but is later used to score responses from a 70B model, it may assign unreliable scores to outputs it has never seen. This distributional mismatch is a primary cause of reward hacking: the policy finds high-reward outputs that exploit blind spots in the RM rather than genuinely improving quality.
\end{warningbox}

\subsection{Stage 3: PPO Fine-Tuning with KL Penalty}

\textbf{What it is.} Use PPO to fine-tune the SFT model to maximize the reward model's score, subject to a KL divergence penalty that prevents the policy from drifting too far from the SFT model.

\begin{mathresult}{RLHF Objective}
\begin{equation}
\max_{\pi_\theta}\; \E_{x \sim \mathcal{D},\; y \sim \pi_\theta(\cdot \mid x)}\left[R_\phi(x, y) - \beta \cdot \KL\!\left(\pi_\theta(\cdot \mid x)\;\|\;\pi_{\text{ref}}(\cdot \mid x)\right)\right]
\end{equation}
where $\pi_{\text{ref}}$ is the frozen SFT model and $\beta$ controls the strength of the KL penalty.
\end{mathresult}

\textbf{Why the KL penalty?} Without it, the policy would exploit the reward model: producing degenerate text that scores high on the (imperfect) RM but is actually nonsensical. The KL term anchors the policy near the SFT model, which we know produces coherent text. $\beta$ controls the exploration-exploitation tradeoff:
\begin{itemize}
    \item \textbf{$\beta$ too high:} Policy barely moves from SFT model; reward gains are minimal.
    \item \textbf{$\beta$ too low:} Policy drifts freely; reward hacking and coherence degradation.
    \item \textbf{Typical range:} $\beta \in [0.01, 0.2]$. Many implementations use adaptive $\beta$ that targets a specific KL budget.
\end{itemize}

\textbf{Models in memory during PPO training.} This is a frequent interview question. Four models must coexist during Stage 3:

\begin{table}[H]
\centering
\caption{Models loaded during PPO-based RLHF training}
\begin{tabularx}{\textwidth}{llX}
\toprule
\textbf{Model} & \textbf{Updated?} & \textbf{Purpose} \\
\midrule
Policy $\pi_\theta$ & Yes (PPO updates) & Generates responses; the model being optimized \\

\textbf{Why this is expensive.} For a 7B policy model, you need $\sim$4 copies of a large model in memory simultaneously ($\sim$56GB in FP16 for parameters alone, plus activations). This is why RLHF is typically done on clusters, and why methods that reduce model count (like DPO) are attractive.

\section{DPO: Direct Preference Optimization}
\label{sec:dpo}
%==============================================================================

\subsection{The Key Insight}

\textbf{What it is.} DPO (Rafailov et al., 2023, NeurIPS) eliminates the reward model entirely by showing that the optimal policy under the RLHF objective has a closed-form relationship with the reward function. Instead of training a separate RM and then running PPO, DPO directly optimizes the policy on preference data using a classification-style loss.

\begin{keyinsight}[DPO's Implicit Reward Model]
The RLHF objective $\max_\pi \E[R(x,y) - \beta \KL(\pi \| \pi_{\text{ref}})]$ has a closed-form optimal policy: $\pi^*(y \mid x) \propto \pi_{\text{ref}}(y \mid x) \exp\!\big(\frac{1}{\beta}R(x,y)\big)$. Rearranging, the reward can be expressed as $R(x,y) = \beta \log \frac{\pi^*(y \mid x)}{\pi_{\text{ref}}(y \mid x)} + \beta \log Z(x)$. DPO substitutes this into the Bradley-Terry preference model, and the partition function $Z(x)$ cancels. The result is a loss that only involves the policy model and the reference model---no reward model needed.
\end{keyinsight}

\begin{mathresult}{DPO Loss}
\begin{equation}
\loss_{\text{DPO}} = -\E_{(x, y_w, y_l)}\left[\log \sigma\!\left(\beta \log \frac{\pi_\theta(y_w \mid x)}{\pi_{\text{ref}}(y_w \mid x)} - \beta \log \frac{\pi_\theta(y_l \mid x)}{\pi_{\text{ref}}(y_l \mid x)}\right)\right]
\end{equation}
The loss increases the log-probability ratio of the preferred response $y_w$ relative to the reference model, while decreasing it for the dispreferred response $y_l$.
\end{mathresult}

\textbf{Interpretation.} Each term $\beta \log \frac{\pi_\theta(y \mid x)}{\pi_{\text{ref}}(y \mid x)}$ is the \textit{implicit reward} the policy assigns to response $y$. DPO trains the policy so that its implicit reward for $y_w$ exceeds that for $y_l$---exactly what the reward model would enforce, but without needing a separate model.

\subsection{DPO vs.\ PPO Comparison}

\centering
\caption{PPO-based RLHF vs.\ DPO for LLM alignment}
\begin{tabularx}{\textwidth}{lXX}
\toprule
\textbf{Dimension} & \textbf{PPO (RLHF)} & \textbf{DPO} \\
\midrule
Reward model & Required (separate model) & Not needed (implicit in policy) \\

\end{tabularx}

\textbf{When to choose PPO:}
\begin{itemize}
    \item You need iterative online data collection (generate, score, improve, repeat).
    \item Your reward signal is non-pairwise (e.g., a verifiable reward like code correctness or math proof checking).
    \item You have the compute infrastructure for the full RL loop.
\end{itemize}

\textbf{When to choose DPO:}
\begin{itemize}
    \item You have a high-quality static preference dataset.
    \item Compute budget is limited (no separate RM, no generation during training).
    \item You want simplicity and reproducibility---DPO is essentially supervised learning.
\end{itemize}

Several improvements to DPO have emerged:

Iterative DPO (generate with current policy $\rightarrow$ collect preferences $\rightarrow$ retrain) partially addresses this but adds complexity.

\section{Reward Hacking and Alignment Tax}
\label{sec:reward_hacking}
%==============================================================================

\subsection{Reward Hacking}

\textbf{What it is.} The policy learns to exploit flaws in the reward model rather than genuinely improving response quality. The reward score goes up, but actual quality (as judged by humans) stagnates or degrades. This is the central failure mode of RLHF.

\textbf{Common manifestations:}
\begin{itemize}
    \item \textbf{Verbosity:} The RM assigns higher scores to longer responses (a learned bias from human annotators who equate length with thoroughness). The policy generates excessively long, repetitive answers.
    \item \textbf{Sycophancy:} The RM rewards agreement. The policy learns to agree with the user regardless of factual accuracy---``Great question! You are absolutely right that the earth is flat.''
    \item \textbf{Formatting tricks:} The policy discovers that bullet points, bold text, and structured formatting increase RM scores, even when the content is shallow.
    \item \textbf{Distribution shift exploitation:} The policy generates outputs outside the RM's training distribution, finding high-reward regions that the RM scores high by extrapolation rather than genuine quality.
\end{itemize}

\textbf{Detection:}
\begin{enumerate}
    \item \textbf{Divergence between RM score and human evaluation.} Track both during training. If RM score keeps climbing but human win-rates plateau or drop, you are hacking.
    \item \textbf{KL divergence monitoring.} Plot KL between the policy and the reference model. If KL grows rapidly, the policy is moving far from the SFT model---likely into hacked territory.
    \item \textbf{Response statistics.} Monitor response length, vocabulary diversity, and formatting patterns. Sudden shifts signal exploitation.
\end{enumerate}

\textbf{Mitigation:}
\begin{enumerate}
    \item \textbf{Stronger KL penalty ($\beta$).} The most direct defense. Tighter KL keeps the policy closer to the SFT model.
    \item \textbf{Reward model ensembles.} Use multiple RMs trained on different data splits. Only reward outputs that score high across all RMs---harder to exploit multiple models simultaneously.
    \item \textbf{Length-normalized reward.} Divide the reward by response length to remove the verbosity incentive.
    \item \textbf{Iterative RM retraining.} As the policy evolves, retrain the RM on outputs from the current policy. This closes the distribution gap.
    \item \textbf{Process reward models (PRMs).} Instead of scoring the entire response, score each step (each sentence or reasoning step). This provides denser, more grounded reward signal and is harder to exploit.
\end{enumerate}

\begin{warningbox}
Reward hacking is not a bug that can be ``fixed'' permanently. It is a fundamental consequence of optimizing against an imperfect proxy (the RM) for a true objective (human satisfaction). Any RM will have exploitable blind spots. The practical goal is not to eliminate reward hacking but to detect it early (via human eval) and mitigate it (via KL constraints, ensembles, and iterative RM updates). Goodhart's Law applies: ``When a measure becomes a target, it ceases to be a good measure.''
\end{warningbox}

\subsection{Alignment Tax}

\textbf{What it is.} The performance cost of aligning a model. RLHF typically improves helpfulness and safety but degrades raw capability on benchmarks like MMLU, HumanEval, or GSM8K. The model becomes ``nicer'' but ``dumber.''

\textbf{Why it happens:}
\begin{itemize}
    \item \textbf{KL penalty constrains exploration.} The model cannot deviate far from the SFT policy, limiting its ability to discover novel solutions.
    \item \textbf{Safety training inhibits capability.} Teaching the model to refuse harmful requests can over-generalize to refusing legitimate but edgy requests (``I cannot help with chemistry'' when asked about baking soda reactions).
    \item \textbf{Reward model bias toward caution.} If annotators reward cautious, hedged answers, the model learns to be less decisive and less willing to commit to correct answers.
\end{itemize}

\textbf{Mitigation:}
\begin{itemize}
    \item \textbf{Minimize SFT-to-RLHF gap.} Use higher-quality SFT data so the starting point is already strong.
    \item \textbf{Capability-specific data in RM training.} Include preference pairs that explicitly reward correct answers on benchmarks, not just ``safe'' answers.
    \item \textbf{Separate safety and helpfulness objectives.} Train separate reward models for safety and helpfulness, then combine with weighted objectives.
    \item \textbf{DPO with careful data curation.} DPO's lighter touch (no RL loop) often incurs a smaller alignment tax than PPO.
\end{itemize}

\section{Constitutional AI and RLAIF}
\label{sec:constitutional_ai}
%==============================================================================

\subsection{Constitutional AI (CAI)}

\textbf{What it is.} An approach developed by Anthropic (Bai et al., 2022) that replaces most human feedback with AI-generated feedback guided by a set of explicit principles (the ``constitution''). The goal: reduce reliance on expensive human annotation while making the value alignment explicit and auditable.

\textbf{How it works:}
\begin{enumerate}
    \item \textbf{Red-teaming generation.} Prompt the model to produce harmful outputs.
    \item \textbf{Self-critique.} Ask the model to critique its own output against a constitutional principle (e.g., ``Is this response harmful? Revise it to be helpful while avoiding harm.'').
    \item \textbf{Revision.} The model generates a revised, improved response.
    \item \textbf{RLAIF.} Use an AI model (not humans) to generate preferences between the original and revised responses. Train the RM on these AI-generated preferences, then run RL as usual.
\end{enumerate}

\textbf{Advantages:}
\begin{itemize}
    \item Scales cheaply (AI feedback is orders of magnitude cheaper than human annotation).
    \item Principles are explicit and can be audited---you know exactly what values the model was trained on.
    \item Reduces human exposure to harmful content during annotation.
\end{itemize}

\textbf{Limitations:}
\begin{itemize}
    \item The AI judge inherits biases from its own training.
    \item The constitution is a blunt instrument---complex ethical tradeoffs are hard to encode as simple rules.
    \item Quality of AI feedback is bounded by the capability of the judge model.
\end{itemize}

\subsection{RLAIF (RL from AI Feedback)}

\textbf{What it is.} The broader paradigm of using AI-generated preference labels instead of human labels. Constitutional AI is one implementation of RLAIF. Others include:

\begin{itemize}
    \item \textbf{LLM-as-judge:} Use a strong model (e.g., GPT-4) to rank outputs of a weaker model, then train the weaker model on those preferences.
    \item \textbf{Self-play / self-improvement:} A model generates, evaluates, and trains on its own outputs. Used in reasoning tasks where correctness is verifiable (math, code).
    \item \textbf{Synthetic data for DPO:} Generate multiple responses, use an AI judge to select $y_w$ and $y_l$, then run DPO.
\end{itemize}

\begin{keyinsight}[RLAIF Works Best When Verification Is Easy]
AI-generated feedback is most reliable when the quality of a response is objectively verifiable: code that passes tests, math with checkable answers, or factual claims that can be looked up. It is least reliable for subjective tasks (creative writing, ethical dilemmas) where even humans disagree. The trend in frontier labs is to use RLAIF for scalable but coarse alignment, then use targeted human feedback for the nuanced cases.
\end{keyinsight}

\subsection{Process vs.\ Outcome Reward Models}

\textbf{Outcome reward models (ORMs):} Score the final response as a whole. Simple but provide sparse reward signal---the model does not know which part of its reasoning was good or bad.

\textbf{Process reward models (PRMs):} Score each intermediate step (e.g., each line of mathematical reasoning). Denser signal leads to more reliable credit assignment and is harder to hack. OpenAI's ``Let's Verify Step by Step'' (Lightman et al., 2023) showed that PRMs significantly improve mathematical reasoning over ORMs.

\textbf{Connection to test-time compute.} PRMs enable search at inference time: generate multiple reasoning paths, score each step, and select the path with the highest cumulative step-level reward. This is the principle behind o1/o3-style reasoning models that trade more inference compute for better answers.

\section{Interview Questions}
\label{sec:rl_interview}
%==============================================================================

%--- Rewritten Q1: Walk through RLHF pipeline ---

\begin{interviewq}
\textbf{Q: Walk me through the RLHF pipeline for aligning an LLM.}

\textbf{Difficulty:} L5 \quad \textbf{Type:} Conceptual \quad \textbf{Frequency:} \freqhigh{}

\textbf{Strong answer:}

RLHF has three stages, each solving a specific problem.

\textbf{Stage 1: Supervised Fine-Tuning (SFT).} Fine-tune the pretrained base model on curated (instruction, response) pairs using cross-entropy loss. This teaches the model the \textit{format}---how to follow instructions and produce conversational responses. Data quality dominates quantity; LIMA showed 1,000 high-quality examples can suffice. Only compute loss on response tokens, not the prompt.

\textbf{Stage 2: Reward Model Training.} Collect human preference data: show annotators a prompt with two model-generated responses and ask which is better. Train a reward model (initialized from the SFT checkpoint, with a scalar head) using the Bradley-Terry loss: $\loss = -\log\sigma(R(x,y_w) - R(x,y_l))$. This model learns to assign higher scores to preferred responses. Typically requires 100K--500K pairwise comparisons.

\textbf{Stage 3: PPO Optimization.} Fine-tune the SFT model using PPO to maximize the reward model's score, with a KL divergence penalty: $\E[R_\phi(x,y) - \beta \cdot \KL(\pi_\theta \| \pi_{\text{ref}})]$. Four models coexist in memory: the policy (being optimized), the reference model (frozen SFT), the reward model (frozen), and the value function (PPO's critic). The KL penalty is critical---without it, the policy will exploit reward model weaknesses (reward hacking).

Each stage has a distinct purpose: SFT teaches format, the RM captures human judgment, and PPO optimizes against that judgment while staying grounded.

\textbf{Red flags} (what NOT to say):
\begin{itemize}
    \item Describing the stages without explaining \textit{why} each exists.
    \item Forgetting the four-model memory requirement in Stage 3.
    \item Claiming SFT alone is sufficient for alignment---SFT teaches format, not judgment.
\end{itemize}

\textbf{What the interviewer is testing:} Can you articulate why each stage exists, not just what it does? The depth signal comes from explaining the KL penalty, the four-model memory cost, and what breaks if any stage is skipped.

\textbf{What separates good from great:}
\begin{itemize}
    \item \textbf{L5:} Correctly names all three stages and explains each at a high level.
    \item \textbf{L6:} Explains why SFT alone is insufficient, derives the KL-penalized objective, and quantifies the memory cost of four models.
    \item \textbf{L7:} Discusses how frontier labs iterate on RLHF (iterative RM retraining, process reward models for reasoning), and connects to DPO as a simpler alternative with different tradeoffs.
\end{itemize}

\textbf{Common follow-ups:} ``Why not skip SFT and go straight to RL from the base model?'' ``How many human preference labels do you need?'' ``What are the alternatives to PPO?''
\end{interviewq}

\begin{interviewq}
\textbf{Q: PPO vs DPO vs RLHF---complete comparison for LLM alignment.}

\textbf{Difficulty:} L6 \quad \textbf{Type:} Trade-off \quad \textbf{Frequency:} \freqhigh{}

\textbf{Strong answer:}

The fundamental distinction is online vs.\ offline. PPO-based RLHF is an \textit{online} RL method: it generates new responses during training, scores them with a reward model, and updates the policy. DPO is an \textit{offline} supervised method: it directly optimizes on a static preference dataset without generation or a reward model.

\textbf{DPO advantages:} (1) Simplicity---supervised learning with no RL loop, no generation during training, no reward model. (2) Compute efficiency---two models in memory (policy + frozen reference) vs.\ four for PPO; training cost is roughly $1.5\times$ SFT vs.\ $3$--$5\times$ for PPO. (3) Lower reward hacking risk---no explicit RM to exploit; the implicit reward is structurally constrained by the log-probability ratio.

\textbf{PPO advantages:} (1) Online exploration---generates and scores new responses, discovering high-quality outputs not in any static dataset. (2) Non-pairwise rewards---works with any scalar reward signal (code correctness, math proof verification, tool use success). (3) Iterative improvement---the generate-score-improve loop naturally adapts to the evolving policy.

\textbf{Decision framework:} Start with DPO when you have high-quality static preference data and limited compute. Switch to PPO when you need iterative online improvement, have a verifiable reward signal, or need the policy to explore beyond existing data. Frontier labs often use both: DPO for initial alignment, then PPO with a process reward model for reasoning capabilities. RLHF remains the umbrella term for the PPO-based pipeline (SFT $\rightarrow$ RM $\rightarrow$ PPO).

\textbf{Red flags} (what NOT to say):
\begin{itemize}
    \item ``DPO is strictly better because it is simpler''---DPO cannot explore beyond its static dataset, which limits it for reasoning tasks.
    \item Confusing RLHF (the pipeline) with PPO (the optimizer)---RLHF refers to the full three-stage process.
    \item Not knowing DPO's implicit reward model ($\beta \log \frac{\pi_\theta(y \mid x)}{\pi_{\text{ref}}(y \mid x)}$).
\end{itemize}

\textbf{What the interviewer is testing:} Whether you understand the online-vs-offline distinction, not just ``DPO has fewer models.'' The strong signal is connecting this to when each approach wins based on data availability, reward signal type, and compute budget.

\textbf{What separates good from great:}
\begin{itemize}
    \item \textbf{L5:} Correctly compares model count, compute cost, and training complexity.
    \item \textbf{L6:} Explains the online-vs-offline tradeoff, articulates when PPO's exploration matters (verifiable rewards, reasoning), and mentions iterative DPO as a middle ground.
    \item \textbf{L7:} Discusses how frontier labs combine both methods in a multi-stage pipeline, mentions DPO variants (KTO for unpaired data, SimPO for length normalization), and reasons about when online RL becomes essential (reasoning models like o1).
\end{itemize}

\textbf{Common follow-ups:} ``What is DPO's implicit reward model?'' ``How would you do iterative DPO?'' ``Can DPO handle non-binary preferences?'' ``Why did Llama 3 use DPO?''
\end{interviewq}

%--- Rewritten Q3: Reward hacking ---

\begin{interviewq}
\textbf{Q: What is reward hacking? Give 3 concrete examples and how to mitigate each.}

\textbf{Difficulty:} L5 \quad \textbf{Type:} Conceptual \quad \textbf{Frequency:} \freqhigh{}

\textbf{Strong answer:}

Reward hacking occurs when the policy optimizes the learned reward model's score without genuinely improving response quality. It is Goodhart's Law applied to RLHF: the RM is an imperfect proxy for human preferences, and the policy finds high-scoring outputs that exploit the proxy's blind spots.

\textbf{Example 1: Verbosity.} The RM assigns higher scores to longer responses (a bias learned from annotators who equate length with effort). The policy generates excessively long, repetitive text. \textit{Mitigation:} Length-normalized reward---divide the reward by response length. Also include preference pairs in RM training where the shorter response is preferred.

\textbf{Example 2: Sycophancy.} The RM rewards agreement. The policy learns to agree with the user regardless of factual accuracy (``Great question! You are absolutely right that the earth is flat.''). \textit{Mitigation:} Include adversarial preference pairs where the truthful-but-disagreeing response is marked as preferred. Train a separate truthfulness reward model and combine signals.

\textbf{Example 3: Distribution shift exploitation.} The policy generates outputs far from the RM's training distribution, landing in regions where the RM extrapolates unreliable high scores. \textit{Mitigation:} Stronger KL penalty ($\beta$) to keep the policy near the reference model; iterative RM retraining on the current policy's outputs to close the distribution gap.

\textbf{Detection:} Track RM score, KL divergence from the reference model, and periodic human evaluation simultaneously. If RM score rises but human win-rates plateau or drop, you are hacking. Secondary signals: response length inflation, vocabulary diversity collapse, formatting pattern changes.

\textbf{Red flags} (what NOT to say):
\begin{itemize}
    \item Treating reward hacking as a bug that can be ``fixed''---it is a fundamental consequence of optimizing imperfect proxies.
    \item Only proposing one mitigation---the interviewer wants to see layered defenses.
    \item Claiming DPO is immune to reward hacking (it can still overfit to biases in preference data).
\end{itemize}

\textbf{What the interviewer is testing:} Understanding that reward hacking is fundamental (Goodhart's Law), not a bug. The strongest candidates give concrete examples, propose specific mitigations for each, and describe a detection methodology.

\textbf{What separates good from great:}
\begin{itemize}
    \item \textbf{L5:} Names 2--3 examples and general mitigations (KL penalty, ensembles).
    \item \textbf{L6:} Pairs each example with a specific mitigation, describes detection methodology (RM score vs.\ human eval divergence), and mentions process reward models as a structural defense.
    \item \textbf{L7:} Connects to the broader alignment landscape---reward hacking in reasoning models (o1-style), the role of verification in mitigating hacking for code/math, and the Pareto frontier between KL budget and alignment gain.
\end{itemize}

\textbf{Common follow-ups:} ``Is DPO immune to reward hacking?'' ``How do process reward models help?'' ``What is the relationship between KL budget and reward hacking?''
\end{interviewq}

\begin{interviewq}
\textbf{Q: Your RLHF-tuned model becomes sycophantic (agrees with everything). Diagnose and fix.}

\textbf{Difficulty:} L6 \quad \textbf{Type:} Debugging \quad \textbf{Frequency:} \freqhigh{}

\textbf{Strong answer:}

\textbf{Symptoms:} The model systematically agrees with user premises even when factually wrong (``You're right, the sun orbits the earth''), avoids contradicting user opinions, and provides overly enthusiastic validation. This is a specific form of reward hacking where the RM inadvertently rewards agreeableness.

\textbf{Diagnosis --- root cause analysis:}

\textbf{Hypothesis 1: RM bias.} The reward model was trained on preference data where annotators systematically preferred agreeable responses. Validation: sample 1,000 preference pairs from the RM training set. Check whether the preferred response agrees with the user's premise in $>$70\% of cases where the premise is debatable or false. If so, the RM encodes a sycophancy bias.

\textbf{Hypothesis 2: KL penalty too low.} With a weak KL constraint, the policy drifted far from the SFT model into a sycophantic mode because it maximizes RM reward. Validation: check the KL divergence from the reference model---if it is $>$20 nats, the policy has drifted significantly.

\textbf{Hypothesis 3: SFT data bias.} The SFT dataset itself may contain sycophantic examples (e.g., assistant data scraped from customer service, where agreement is standard). The model learned sycophancy before RLHF even started.

\textbf{Fixes (layered):}
\begin{enumerate}
    \item \textbf{Curate adversarial preference data.} Create preference pairs where the truthful-but-disagreeing response is marked as preferred over the agreeable-but-wrong response. Retrain the RM.
    \item \textbf{Increase $\beta$.} Tighter KL keeps the policy closer to the SFT model, limiting sycophantic drift.
    \item \textbf{Add a truthfulness reward signal.} Train a separate truthfulness classifier or use a factual consistency checker. Combine its score with the RM reward: $R_{\text{total}} = R_{\text{RM}} + \alpha \cdot R_{\text{truth}}$.
    \item \textbf{Constitutional AI approach.} Add a principle: ``If the user makes a factual error, politely correct them rather than agreeing.'' Generate self-critique and revision pairs targeting sycophancy.
    \item \textbf{Evaluation.} Build a sycophancy benchmark: queries with false premises where the correct response disagrees. Track the disagreement rate across RLHF iterations.
\end{enumerate}

\textbf{Red flags} (what NOT to say):
\begin{itemize}
    \item ``Just add more data''---without diagnosing which data (RM training, SFT, or prompts) caused the problem.
    \item Blaming the model architecture---sycophancy is a data and objective problem, not an architecture problem.
    \item Proposing to fix it only at inference time (e.g., prompt engineering)---this is a training-level issue.
\end{itemize}

\textbf{What the interviewer is testing:} Systematic debugging: can you separate RM bias from KL drift from SFT contamination? Do you propose data-level fixes (not just hyperparameter tweaks)? Do you build a targeted evaluation to verify the fix?

\textbf{What separates good from great:}
\begin{itemize}
    \item \textbf{L5:} Identifies sycophancy as an RM bias problem and proposes increasing $\beta$.
    \item \textbf{L6:} Diagnoses multiple root causes (RM, KL, SFT data), proposes adversarial preference data curation, and builds a sycophancy-specific benchmark.
    \item \textbf{L7:} Discusses the sycophancy-helpfulness tradeoff (over-correcting creates an adversarial model that disagrees unnecessarily), proposes a multi-objective reward that balances truthfulness and helpfulness, and connects to Constitutional AI as a scalable solution.
\end{itemize}

\textbf{Common follow-ups:} ``How do you measure sycophancy quantitatively?'' ``How do you avoid over-correcting into adversarial disagreement?'' ``Can DPO solve this without a reward model?''
\end{interviewq}

\begin{interviewq}
\textbf{Q: Estimate the memory required to run RLHF (4 models: policy, reference, reward model, critic).}

\textbf{Difficulty:} L6 \quad \textbf{Type:} Estimation \quad \textbf{Frequency:} \freqmed{}

\textbf{Strong answer:}

Consider RLHF for a 7B parameter LLM. Four models must coexist in GPU memory.

\textbf{Model weights:}
\begin{itemize}
    \item Policy $\pi_\theta$ (7B, FP16): $7 \times 10^9 \times 2$ bytes = 14 GB.
    \item Reference $\pi_{\text{ref}}$ (7B, FP16, frozen): 14 GB. No optimizer states since it is not trained.
    \item Reward model $R_\phi$ (7B, FP16, frozen): 14 GB. Often the same architecture as the policy with a scalar head.
    \item Value function / critic $V_\psi$: Typically a smaller model or shares the policy backbone with a separate head. Assume a full 7B copy: 14 GB.
    \item \textbf{Subtotal weights:} $4 \times 14 = 56$ GB.
\end{itemize}

\textbf{Optimizer states (for policy and critic only):}
\begin{itemize}
    \item AdamW stores two momentum buffers per parameter in FP32: $2 \times 4 \times P$ bytes per trained model.
    \item Policy: $2 \times 4 \times 7\text{B} = 56$ GB optimizer states + 28 GB FP32 master weights $= 84$ GB.
    \item Critic: another $\sim$84 GB if full-size.
    \item \textbf{Subtotal optimizer:} $\sim$168 GB.
\end{itemize}

\textbf{Activations and KV cache:} During the generation phase, the policy generates sequences (typically 512--2048 tokens). KV cache for batch size 32 at 2K tokens for a 7B model $\approx$ 2--4 GB. Activations for backward pass: 5--15 GB depending on batch size and gradient checkpointing.

\textbf{Total estimate:} $56 + 168 + 15 = \sim$240 GB for a 7B RLHF run. This requires at least 4$\times$A100-80GB or 3$\times$H100-80GB with model parallelism.

\textbf{How to reduce:} (1) Use LoRA for the policy---reduces trainable parameters from 7B to $\sim$20M, slashing optimizer states from 84 GB to $<$1 GB. (2) Quantize the frozen reference and reward models to INT8 (7 GB each instead of 14 GB). (3) Share the policy backbone with the critic (add a value head instead of a separate model). (4) Use DPO instead---eliminates the reward model and critic entirely, reducing to 2 models.

\textbf{Red flags} (what NOT to say):
\begin{itemize}
    \item Forgetting optimizer states---they dominate memory for trained models.
    \item Assuming all four models need optimizer states (only policy and critic are trained).
    \item ``Just use a bigger GPU''---show you can reason about memory reduction strategies.
\end{itemize}

\textbf{What the interviewer is testing:} Can you do back-of-envelope memory math for a multi-model training setup? Do you know which models are frozen vs.\ trained and the memory implications of each?

\textbf{What separates good from great:}
\begin{itemize}
    \item \textbf{L5:} Correctly computes weight memory for 4 models ($\sim$56 GB at FP16) and identifies the setup as expensive.
    \item \textbf{L6:} Adds optimizer states for trained models, arrives at $\sim$240 GB total, and proposes LoRA and quantization to reduce cost.
    \item \textbf{L7:} Discusses ZeRO-3/FSDP sharding across GPUs, compares the memory profile of RLHF vs.\ DPO (2 models, $\sim$50 GB total with LoRA), and reasons about the minimum viable hardware for a given model size.
\end{itemize}

\textbf{Common follow-ups:} ``What is the minimum hardware for RLHF on a 70B model?'' ``How does LoRA change the memory equation?'' ``Compare RLHF memory vs.\ DPO memory.''

%--- New Q6: KL penalty first principles ---

\begin{interviewq}
\textbf{Q: Why does the KL penalty matter in RLHF? What happens without it?}

\textbf{Difficulty:} L5 \quad \textbf{Type:} First Principles \quad \textbf{Frequency:} \freqhigh{}

\textbf{Strong answer:}

The KL penalty $\beta \cdot \KL(\pi_\theta \| \pi_{\text{ref}})$ serves as a regularizer that anchors the trained policy $\pi_\theta$ near the reference model $\pi_{\text{ref}}$ (typically the SFT model). It exists because the reward model is an imperfect proxy for human preferences, and unconstrained optimization against an imperfect proxy produces degenerate behavior.

\textbf{What happens without it:}
\begin{enumerate}
    \item \textbf{Reward hacking.} The policy freely explores the output space and discovers degenerate text that scores high on the RM but is nonsensical or harmful to humans. Without the KL anchor, there is nothing preventing the policy from moving into out-of-distribution regions where the RM gives unreliable scores.
    \item \textbf{Mode collapse.} The policy collapses to a narrow set of high-reward templates. Diversity disappears---the model gives the same formulaic response regardless of the query.
    \item \textbf{Coherence degradation.} The pretrained model's language fluency is a property of its parameter distribution. Large updates during RL can corrupt this distribution, producing text that is grammatically broken or incoherent.
    \item \textbf{Catastrophic forgetting.} General capabilities learned during pretraining (math, coding, factual knowledge) degrade as the policy drifts far from its initialization.
\end{enumerate}

\textbf{The $\beta$ tradeoff:} $\beta$ controls the exploration-exploitation balance. Too high: the policy barely moves from the SFT model and alignment gains are minimal. Too low: the policy drifts freely, causing reward hacking and quality degradation. Typical range is $\beta \in [0.01, 0.2]$. Many implementations use \textit{adaptive $\beta$} that targets a specific KL budget (e.g., target 5 nats; increase $\beta$ if KL exceeds target, decrease if below).

\textbf{Mathematical intuition:} The KL-penalized objective $\max_\pi \E[R(y) - \beta \KL(\pi \| \pi_{\text{ref}})]$ has a closed-form optimal solution: $\pi^*(y) \propto \pi_{\text{ref}}(y) \exp(R(y)/\beta)$. This is the \textit{Boltzmann policy}---it reweights the reference distribution by exponentiated reward. The KL penalty ensures the optimal policy is a smooth reweighting rather than a degenerate point mass.

\textbf{Red flags} (what NOT to say):
\begin{itemize}
    \item ``KL prevents overfitting''---while related, the precise problem is reward model exploitation, not overfitting to training data.
    \item Not knowing what happens when $\beta$ is too high vs.\ too low.
    \item Describing KL penalty as optional or a minor detail---it is fundamental to RLHF stability.
\end{itemize}

\textbf{What the interviewer is testing:} Do you understand \textit{why} RLHF needs a KL constraint (imperfect RM proxy), not just that it uses one? Can you reason about the consequences of removing it?

\textbf{What separates good from great:}
\begin{itemize}
    \item \textbf{L5:} Explains that KL prevents reward hacking and keeps the policy near the reference model.
    \item \textbf{L6:} Discusses the $\beta$ tradeoff with concrete values, mentions adaptive $\beta$, and connects KL to the closed-form Boltzmann policy.
    \item \textbf{L7:} Connects to DPO (which has the KL constraint built into the loss), discusses how frontier labs monitor KL during training as an early warning for reward hacking, and reasons about whether KL against $\pi_{\text{ref}}$ is the right anchor (vs.\ KL against $\pi_{\text{SFT}}$ or a mixture).
\end{itemize}

\textbf{Common follow-ups:} ``How do you choose $\beta$?'' ``What is adaptive KL targeting?'' ``Does DPO also have a KL constraint?'' (Yes---it is implicit in the loss function.)
\end{interviewq}

\begin{interviewq}
\textbf{Q: Design a reward model training pipeline. What data do you need?}

\textbf{Difficulty:} L6 \quad \textbf{Type:} Architecture Design \quad \textbf{Frequency:} \freqmed{}

\textbf{Strong answer:}

\textbf{Step 1: Data collection.} The core input is human preference data: (prompt, response\_A, response\_B, preference). Two approaches to generating response pairs:
\begin{itemize}
    \item \textbf{Same-model pairs:} Generate $K$ responses per prompt from the SFT model using different temperatures or sampling seeds. Annotators rank pairs. This is the standard for initial RLHF.
    \item \textbf{Cross-model pairs:} Include responses from models of different quality levels. This increases the dynamic range of preferences---clearly bad vs.\ clearly good is easier to learn from than two mediocre responses that differ subtly.
\end{itemize}

\textbf{Step 2: Annotation design.} Annotators should evaluate on multiple axes: helpfulness, truthfulness, safety, and instruction-following. Provide clear rubrics with examples. Typical inter-annotator agreement is 70--80\% (the task is inherently subjective). Best practice: collect 3--5 annotations per pair and use majority vote or Elo-style aggregation. Budget: 100K--500K preference pairs for frontier models.

\textbf{Step 3: Architecture.} Initialize from the SFT model checkpoint---the RM should share the same tokenizer, context window, and linguistic representations. Replace the language modeling head with a scalar output head (linear layer $\rightarrow$ single scalar). Input is the concatenation of prompt + response; output is a single reward score. The RM is trained with the Bradley-Terry loss: $\loss = -\log\sigma(R(x, y_w) - R(x, y_l))$.

\textbf{Step 4: Training.} Typical hyperparameters: learning rate $\sim$1e-5 (lower than SFT to avoid forgetting pretrained representations), batch size 64--128 preference pairs, 1--3 epochs (overtraining causes overfitting to annotation noise). Evaluate on a held-out preference test set; track accuracy, calibration, and agreement with held-out annotator labels.

\textbf{Step 5: Validation and failure modes.}
\begin{itemize}
    \item Check for length bias: does the RM systematically score longer responses higher? Plot reward vs.\ response length.
    \item Check for formatting bias: does the RM prefer bullet points or markdown regardless of content?
    \item Check distribution coverage: will the RM generalize to the policy's outputs during PPO, or only to the SFT model's distribution? Generate test responses from a more capable model and check RM ranking accuracy.
\end{itemize}

\textbf{Red flags} (what NOT to say):
\begin{itemize}
    \item Treating the RM as a simple classifier without discussing distribution shift.
    \item Not mentioning annotation quality controls (inter-annotator agreement, rubrics).
    \item Ignoring known biases (length, formatting) that the RM can inherit from annotators.
\end{itemize}

\textbf{What the interviewer is testing:} End-to-end pipeline design, not just the loss function. Do you think about data collection, annotation quality, bias detection, and distribution shift?

\textbf{What separates good from great:}
\begin{itemize}
    \item \textbf{L5:} Describes the Bradley-Terry loss and explains that the RM predicts which response humans prefer.
    \item \textbf{L6:} Designs the full pipeline: data collection strategy, annotation rubrics, architecture initialization, bias auditing, and held-out evaluation.

%--- New Q9: KL penalty and the Boltzmann policy ---

\begin{interviewq}
\textbf{Q: Your RLHF training shows the reward score plateauing while KL divergence keeps climbing. What is happening?}

\textbf{Difficulty:} L7 \quad \textbf{Type:} Debugging \quad \textbf{Frequency:} \freqlow{}

\textbf{Strong answer:}

This pattern---reward plateau with rising KL---indicates the policy has found a local optimum in reward space and is spending its ``KL budget'' on changes that do not improve reward. It is a strong signal that the training dynamics are unhealthy, and continued training will degrade the model.

\textbf{Diagnosis path:}

\textbf{1. Reward model saturation.} The RM has a finite scoring range. The policy may have reached the RM's ceiling---all its outputs now score near the maximum. Further policy updates change the outputs (increasing KL) but cannot push the RM score higher. \textit{Validation:} Plot the distribution of RM scores over recent batches. If they are clustered near the maximum ($>$95th percentile of the RM's score range), the RM is saturated.

\textbf{2. Reward hacking with diminishing returns.} The policy found one hacking strategy (e.g., verbosity) that initially boosted reward, and now it is exploring variations of that strategy (different verbose patterns) without finding higher-reward alternatives. Each variation is far from the reference (KL rises) but scores the same on the RM (reward plateaus). \textit{Validation:} Inspect generated samples. Look for formulaic patterns, length inflation, or repetitive structures.

\textbf{3. Adaptive $\beta$ malfunction.} If using adaptive $\beta$ with a KL target, the $\beta$ may be decreasing too aggressively, allowing KL to grow without corresponding reward gains. The controller is chasing the KL target instead of optimizing the actual objective. \textit{Validation:} Plot $\beta$ over time. If it is monotonically decreasing, the controller may need dampening or a $\beta$ floor.

\textbf{Fixes:}
\begin{enumerate}
    \item \textbf{Stop training.} The best checkpoint is likely in the past, before the KL climb without reward gain. Evaluate recent checkpoints on a held-out human eval set and select the one with the best quality-KL tradeoff.
    \item \textbf{Increase $\beta$ or set a hard KL ceiling.} Prevent further KL growth. If using adaptive $\beta$, set a minimum $\beta$ floor.
    \item \textbf{Retrain the RM.} If the RM is saturated, expand its training data with harder preference pairs from the current policy's outputs. A more discriminating RM creates room for meaningful reward improvement.
    \item \textbf{Switch to process rewards.} If outcome rewards have plateaued, per-step rewards may provide a richer gradient signal.
\end{enumerate}

\textbf{Red flags} (what NOT to say):
\begin{itemize}
    \item ``Just train longer''---rising KL with flat reward means the model is getting worse, not better.
    \item Not checking the RM's score distribution---saturation is the most common cause.
    \item Ignoring the $\beta$ controller as a source of the problem.
\end{itemize}

\textbf{What the interviewer is testing:} Advanced RLHF debugging intuition. Can you read the training curves and form hypotheses? Do you know when to stop training?

\textbf{What separates good from great:}
\begin{itemize}
    \item \textbf{L5:} Identifies that the policy is drifting without gaining reward and suggests stopping training.
    \item \textbf{L6:} Diagnoses RM saturation vs.\ reward hacking, proposes RM retraining, and discusses the $\beta$ tradeoff.
    \item \textbf{L7:} Reasons about adaptive $\beta$ controllers, proposes process reward models as a solution, and frames this as a multi-objective optimization problem (reward vs.\ KL) where checkpoints should be selected on the Pareto frontier.
\end{itemize}

\textbf{Common follow-ups:} ``How do you select the best checkpoint from an RLHF run?'' ``What is the Pareto frontier between reward and KL?'' ``How would you design a better adaptive $\beta$ controller?''
\end{interviewq}

\begin{interviewq}
\textbf{Q: Process reward models vs outcome reward models---what are the tradeoffs and when does each win?}

\textbf{Difficulty:} L6 \quad \textbf{Type:} Trade-off \quad \textbf{Frequency:} \freqmed{}

\textbf{Strong answer:}

\textbf{Outcome reward models (ORMs)} score the entire response with a single scalar. Input: (prompt, full response). Output: one score. This is the standard in RLHF. \textit{Strength:} Simple to train---preference annotation is at the response level, which is natural for human annotators. \textit{Weakness:} Sparse reward signal. The model does not know which part of its response was good or bad. Credit assignment is entirely left to the RL algorithm (PPO's advantage estimator), which is noisy for long responses.

\textbf{Process reward models (PRMs)} score each intermediate step (sentence, reasoning step, or paragraph). Input: (prompt, response up to step $t$). Output: one score per step. \textit{Strength:} Dense reward signal enables precise credit assignment---the model knows exactly which step was good or bad. Harder to hack because each step must independently score well. Enables search at inference time: generate multiple reasoning paths, score each step, prune bad branches. \textit{Weakness:} Requires step-level annotations, which are much more expensive. Human annotators must evaluate each reasoning step for correctness---annotation cost scales linearly with response length.

\textbf{When ORMs win:} Short responses, subjective tasks (creative writing, customer service), and when annotation budget is limited. Most alignment tasks (safety, helpfulness) are well-served by outcome-level reward.

\textbf{When PRMs win:} Multi-step reasoning (math, code, logical deduction), long-form generation where specific steps can be independently evaluated, and when you want to enable test-time search over reasoning paths. OpenAI's ``Let's Verify Step by Step'' (Lightman et al., 2023) showed PRMs significantly outperform ORMs on mathematical reasoning.

\textbf{Connection to reasoning models:} PRMs are foundational to o1/o3-style reasoning. At inference, generate multiple chain-of-thought paths, score each step with the PRM, and use beam search or MCTS to find the highest-scoring path. This trades inference compute for accuracy---more compute at test time produces better answers.

\textbf{Red flags} (what NOT to say):
\begin{itemize}
    \item ``PRMs are strictly better''---they are much more expensive to train and annotate.
    \item Not mentioning the annotation cost difference---this is the primary practical barrier.
    \item Confusing PRMs with chain-of-thought prompting---PRMs are trained models, not prompting techniques.
\end{itemize}

\textbf{What the interviewer is testing:} Understanding the credit assignment problem in RLHF and how PRMs address it. Do you know the practical tradeoffs (annotation cost, training complexity, inference-time search)?

\textbf{What separates good from great:}
\begin{itemize}
    \item \textbf{L5:} Explains that PRMs give per-step feedback while ORMs give per-response feedback.
    \item \textbf{L6:} Discusses the credit assignment advantage, annotation cost tradeoff, and when each is appropriate. Mentions Lightman et al.
    \item \textbf{L7:} Connects PRMs to test-time compute scaling (search over reasoning paths), discusses automated PRM annotation strategies (using code execution or proof verifiers instead of humans), and frames PRMs as enabling a new paradigm where inference compute can substitute for training compute.
\end{itemize}

\textbf{Common follow-ups:} ``How do you annotate step-level labels efficiently?'' ``Can you train a PRM without human step-level labels?'' ``How does test-time search with PRMs scale?''
\end{interviewq}
