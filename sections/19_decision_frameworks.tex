\chapter{Decision Frameworks: When to Use What}
\label{chap:decision_frameworks}

\begin{tldr}
This chapter provides decision frameworks for architecture selection, loss function choice, model sizing, and common trade-offs. Staff-level interviews often test whether you can make principled decisions given constraints—not just whether you know techniques. These frameworks encode best practices and help structure your thinking during system design questions.
\end{tldr}

\subsection{Model Size vs. Data Size}

\begin{keyinsight}[Chinchilla Scaling]
For a fixed compute budget, optimal performance is achieved when:
\begin{equation}
N \approx 20 \times D
\end{equation}
where $N$ is parameters and $D$ is tokens seen during training.

Previous models (GPT-3) were undertrained: too many parameters, too little data.
\end{keyinsight}

\section{Common Trade-off Discussions}

\subsection{Accuracy vs. Latency}

\textbf{Techniques to improve latency while preserving accuracy}:
\begin{enumerate}
    \item \textbf{Quantization}: INT8 gives 2-4× speedup with < 1\% accuracy loss
    \item \textbf{Distillation}: Smaller student can retain 95-99\% of teacher quality
    \item \textbf{Pruning}: Structured pruning for real speedup
    \item \textbf{Caching}: Cache embeddings, predictions for repeated inputs
    \item \textbf{Early exit}: Stop processing when confident
\end{enumerate}

\centering
\caption{Latency reduction techniques}

\toprule

\midrule
INT8 quantization & 2-4× & < 1\% loss & Low \\
INT4 quantization & 4-8× & 1-3\% loss & Medium \\
Distillation & 2-10× & 1-5\% loss & Medium \\

\subsection{Training Cost vs. Inference Cost}

\textbf{When to invest in training}:
\begin{itemize}
    \item High inference volume amortizes training cost
    \item One-time training, many inference calls
    \item Training enables smaller inference model (distillation)
\end{itemize}

\textbf{When to minimize training}:
\begin{itemize}
    \item Rapid iteration needed
    \item Low inference volume
    \item Frequently changing requirements
\end{itemize}

\begin{keyinsight}[Start Simple, Add Complexity]
Always start with the simplest solution that could work:
\begin{enumerate}
    \item Baseline: Logistic regression / simple heuristics
    \item First ML: Gradient boosting for tabular, pretrained BERT for text
    \item Optimize: Custom architectures, ensemble, SOTA methods
\end{enumerate}
Add complexity only when simpler approaches fail to meet requirements.
\end{keyinsight}

\subsection{Production Performance Degradation}

\begin{enumerate}
    \item \textbf{Check data pipeline}
    \begin{itemize}
        \item Feature distributions changed?
        \item Missing/null values increased?
        \item Data source changed?
    \end{itemize}
    
    \item \textbf{Check for data drift}
    \begin{itemize}
        \item Compare feature distributions over time
        \item PSI (Population Stability Index) > 0.25 indicates significant drift
    \end{itemize}
    
    \item \textbf{Segment analysis}
    \begin{itemize}
        \item Performance by user segment
        \item Performance by feature value ranges
        \item Identify affected subpopulations
    \end{itemize}
    
    \item \textbf{Model debugging}
    \begin{itemize}
        \item Feature importance analysis
        \item Error analysis on failing cases
        \item Compare to baseline/previous model
    \end{itemize}
\end{enumerate}

\section{Interview Question Patterns}
\label{sec:interview_patterns}
%==============================================================================

\subsection{System Design Questions}

\textbf{Common patterns}:
\begin{enumerate}
    \item Clarify requirements and constraints
    \item Propose high-level architecture
    \item Dive into ML components
    \item Discuss trade-offs
    \item Address scale and production concerns
\end{enumerate}

\begin{interviewq}
\textbf{Q: Design a content recommendation system for a news app.}

\textbf{Difficulty:} L6 \quad \textbf{Type:} Architecture Design \quad \textbf{Frequency:} \freqhigh{}

\textbf{Strong answer:} \textbf{Step 1---Clarify requirements}: Scale (users, articles/day), latency SLA ($<$200ms), cold-start handling, engagement metric to optimize (CTR, session time, retention). \textbf{Step 2---Architecture}: Two-stage system. Candidate generation: two-tower model (user tower encoding history + demographics, item tower encoding article content + metadata) with ANN retrieval over all articles. Returns top 200 candidates in $<$10ms. Ranking: a cross-encoder or feature-rich neural ranker scores the 200 candidates using user-item cross-features, session context, and real-time signals. Returns top 20 in $<$50ms. Business logic layer applies diversity constraints, freshness boost, and brand safety filters. \textbf{Step 3---Key decisions}: Two-tower for retrieval (latency) vs.\ cross-encoder for ranking (quality). Batch user embeddings with real-time session overlay. Exploration: epsilon-greedy or Thompson sampling to discover new user preferences. \textbf{Step 4---Production}: A/B test with CTR primary, retention guardrail, diversity guardrail. Feedback loop monitoring: if the model keeps showing the same content types, diversity decays. Daily model retraining. Feature store for user history (batch) and session context (streaming).

\textbf{Red flags} (what NOT to say):
\begin{itemize}
    \item Jumping to model architecture without clarifying requirements
    \item Single-stage design (no retrieval/ranking separation)
    \item No mention of cold start, exploration, or feedback loops
\end{itemize}

\textbf{What the interviewer is testing:} End-to-end ML system design. Do you start with requirements? Do you design beyond the model?

\textbf{What separates good from great:}
\begin{itemize}
    \item \textbf{L5:} Two-stage architecture, correct metric choice, basic feature engineering
    \item \textbf{L6:} Diversity constraints, exploration strategy, feedback loop awareness, A/B testing plan
    \item \textbf{L7:} Multi-objective optimization (CTR + retention + diversity), position bias in training data, long-term user ecosystem health, organizational incentive alignment
\end{itemize}

\textbf{Common follow-ups:} ``How do you handle cold-start users?'' ``How do you avoid filter bubbles?'' ``How do you balance freshness vs.\ relevance?''
\end{interviewq}

\subsection{Architecture Choice Questions}

\textbf{Pattern}: ``Would you use X or Y for this problem?''

\textbf{Framework}:
\begin{enumerate}
    \item State your choice clearly
    \item Explain the primary reason
    \item Acknowledge trade-offs
    \item Describe when you'd choose the alternative
\end{enumerate}

\begin{interviewq}
\textbf{Q: Design the ML architecture for a content moderation system.}

\textbf{Difficulty:} L6 \quad \textbf{Type:} Architecture Design \quad \textbf{Frequency:} \freqhigh{}

\textbf{Strong answer:} Content moderation requires high recall (must catch violations) with acceptable precision (minimize false blocks) at massive scale and low latency. \textbf{Architecture---three-level cascade}: \textbf{Level 1---Rules and heuristics} (0.1ms): Keyword/regex filters, known-bad URL blocklists, exact-match against known violating content hashes (PhotoDNA-style). Catches 50--60\% of violations at near-zero cost. \textbf{Level 2---Fast classifiers} (5--10ms): Small BERT or distilled model for text. EfficientNet for images. Multi-label classification: hate speech, violence, NSFW, spam, misinformation. Catches 35\% of remaining violations. Route uncertain cases (confidence 0.3--0.7) to Level 3. \textbf{Level 3---Heavy models + human review}: Large multimodal model for complex cases (sarcasm, context-dependent content, memes). Human review queue for high-stakes decisions (legal liability). \textbf{Key design decisions}: (1) Threshold tuning per category---higher recall for child safety (accept more false positives) vs.\ lower recall for borderline political content (avoid censorship). (2) Multi-modal: text, image, video, audio all need separate or unified models. (3) Adversarial robustness: users deliberately obfuscate violating content (Unicode tricks, image perturbations). (4) Appeal system: false positives need a review path. \textbf{Metrics}: Per-category precision and recall, latency per level, human review volume, false positive appeal rate. \textbf{Production}: Continuous retraining on new violation patterns. Active learning from human review queue.

\textbf{Red flags} (what NOT to say):
\begin{itemize}
    \item Single model for all moderation---ignores the latency/cost cascade
    \item Not differentiating recall requirements by violation category
    \item Ignoring the adversarial nature of the problem
\end{itemize}

\textbf{What the interviewer is testing:} Can you design a multi-stage system with different precision/recall requirements per category? Do you think about adversarial robustness and scale?

\textbf{What separates good from great:}
\begin{itemize}
    \item \textbf{L5:} Cascade architecture, per-category thresholds, multi-modal awareness
    \item \textbf{L6:} Adversarial robustness, appeal system, active learning from human review, cost analysis
    \item \textbf{L7:} Discusses policy-model alignment (translating policy guidelines into model labels), cross-cultural content differences, legal and regulatory requirements, organizational governance
\end{itemize}

\textbf{Common follow-ups:} ``How do you handle sarcasm and context?'' ``How do you deal with adversarial attacks on the moderation system?'' ``How do you balance precision and recall for borderline content?''
\end{interviewq}

\subsection{Trade-off Discussion Questions}

\textbf{Pattern}: ``How would you handle X constraint?''

\textbf{Framework}:
\begin{enumerate}
    \item Acknowledge the constraint explicitly
    \item List options with trade-offs
    \item Recommend based on typical scenarios
    \item Ask clarifying questions if needed
\end{enumerate}

\begin{interviewq}
\textbf{Q: Your model needs to run in $<$10ms. Current latency is 50ms. Walk through the optimization decision tree.}

\textbf{Difficulty:} L6 \quad \textbf{Type:} Trade-off \quad \textbf{Frequency:} \freqhigh{}

\textbf{Strong answer:} This requires a 5$\times$ speedup. I approach systematically. \textbf{Step 1---Profile the bottleneck}: Break latency into components: feature computation, model forward pass, post-processing, network overhead. Fix the bottleneck, not everything. If feature computation is 30ms, no model optimization will help---you need feature precomputation or caching. \textbf{Step 2---Low-effort optimizations} (try first): INT8 quantization gives 2--4$\times$ speedup with $<$1\% quality loss. Graph optimization (TensorRT, ONNX Runtime) fuses operators for 1.5--3$\times$. Flash attention if attention is the bottleneck. These combined might get us from 50ms to 15--20ms. \textbf{Step 3---Medium-effort} (if still insufficient): Model distillation---train a smaller student to mimic the large model. A 12-layer BERT distilled to 3 layers gives $\sim$4$\times$ speedup at 95--97\% quality. Structured pruning: remove attention heads and layers that contribute least. \textbf{Step 4---Architectural changes} (if needed): Replace the model entirely with a smaller architecture (DistilBERT, TinyBERT, or a shallow model). Caching frequent predictions eliminates inference entirely for repeated inputs. Early exit: if the model is confident after 2 layers, skip the remaining 10. \textbf{Step 5---System-level}: Better hardware (GPU with tensor cores). Serving optimization (dynamic batching for throughput, not latency). Pre-computation of expensive sub-computations. \textbf{My recommendation}: Profile first (30 min). Then INT8 + TensorRT ($\sim$3--4$\times$, 1 day effort). If not enough, distillation ($\sim$1--2 week effort).

\textbf{Red flags} (what NOT to say):
\begin{itemize}
    \item ``Just use a smaller model'' without profiling the actual bottleneck
    \item Not ordering optimizations by effort-to-impact ratio
    \item Forgetting feature computation latency (often the real bottleneck)
\end{itemize}

\textbf{What the interviewer is testing:} Systematic optimization thinking. Do you profile before optimizing? Do you order by effort-to-impact?

\textbf{What separates good from great:}
\begin{itemize}
    \item \textbf{L5:} Profiles first, knows quantization and distillation, orders by effort
    \item \textbf{L6:} Includes graph optimization, caching, early exit. Gives time estimates for each approach
    \item \textbf{L7:} Analyzes whether the latency SLA should be renegotiated (is 10ms truly necessary?), proposes a Pareto analysis of quality vs.\ latency, discusses the organizational process for making this tradeoff
\end{itemize}

\textbf{Common follow-ups:} ``What if quantization causes a 3\% accuracy drop?'' ``How do you decide between distillation and pruning?'' ``What if the model is already INT8?''
\end{interviewq}

\begin{interviewq}
\textbf{Q: You have 3 months and a team of 3 ML engineers. Should you fine-tune an LLM or train a custom model?}

\textbf{Difficulty:} L6 \quad \textbf{Type:} Trade-off \quad \textbf{Frequency:} \freqhigh{}

\textbf{Strong answer:} This is a build-vs-adapt decision. The answer depends on five factors. \textbf{1. Task specificity}: If the task is well-served by language understanding (classification, extraction, summarization, QA), fine-tune an LLM---you get strong baseline performance immediately and can iterate on data quality rather than architecture. If the task involves structured inputs (tabular data, time series, graph data), a custom model is necessary because LLMs do not handle these well. \textbf{2. Data volume and quality}: With $<$10K labeled examples, fine-tuning a pre-trained LLM via LoRA is almost always better---it leverages the model's pre-existing knowledge. With $>$100K examples and a well-defined task, a custom model (BERT-size or smaller) may be more efficient to serve and iterate on. \textbf{3. Latency and cost}: An LLM (even fine-tuned) typically requires $>$20ms for inference on GPU. A distilled BERT or lightweight custom model can serve in $<$5ms. If you need $<$10ms at 100K+ QPS, a custom smaller model is likely better. \textbf{4. Iteration speed}: Fine-tuning an LLM gives you a working prototype in days. A custom model requires architecture search, hyperparameter tuning, and more engineering time. With 3 months and 3 engineers, I would spend month 1 on LLM fine-tuning to establish a strong baseline and validate the approach with stakeholders, then months 2--3 either iterating on the LLM pipeline (data quality, prompt engineering, evaluation) or distilling to a smaller custom model if serving cost requires it. \textbf{5. Team expertise}: If the team has strong NLP experience, a custom model is feasible. If they are generalists, LLM fine-tuning has a much lower skill barrier.

\textbf{Red flags} (what NOT to say):
\begin{itemize}
    \item ``Always fine-tune an LLM''---ignores serving cost, latency, and task-type constraints
    \item ``Always build custom''---wastes months when an LLM baseline would work in days
    \item Not considering the team's expertise as a factor
\end{itemize}

\textbf{What the interviewer is testing:} Engineering judgment under resource constraints. Can you make a principled decision that accounts for team size, timeline, and technical factors?

\textbf{What separates good from great:}
\begin{itemize}
    \item \textbf{L5:} Considers data volume, task type, and latency requirements
    \item \textbf{L6:} Proposes a phased approach (LLM baseline first, then optimize), discusses the distillation path from LLM to custom model
    \item \textbf{L7:} Factors in organizational context (team growth, long-term maintenance, vendor lock-in), proposes success criteria for the phase-1/phase-2 decision gate
\end{itemize}

\textbf{Common follow-ups:} ``What if the task involves both text and tabular data?'' ``How do you evaluate whether the LLM baseline is good enough?'' ``When would you switch from LoRA to full fine-tuning?''
\end{interviewq}

\begin{interviewq}
\textbf{Q: GPU vs TPU vs CPU for inference---give a decision framework for different workloads.}

\textbf{Difficulty:} L5 \quad \textbf{Type:} Trade-off \quad \textbf{Frequency:} \freqmed{}

\textbf{Strong answer:} The choice depends on workload characteristics: model size, batch size, latency requirements, and cost. \textbf{CPU inference}: Best for small models (logistic regression, small gradient boosting, shallow networks $<$10M params), low batch sizes, or when the workload is memory-bound not compute-bound. Advantages: cheapest per instance, no GPU driver complexity, scales horizontally easily. Use for: feature-based ML models, lightweight classifiers, edge deployment. \textbf{GPU inference}: Best for large neural networks (transformers, CNNs $>$100M params) that benefit from massive parallelism. Advantages: 10--100$\times$ throughput over CPU for matrix-heavy workloads, tensor cores accelerate FP16/INT8. Use for: LLM inference, image/video models, any model where the forward pass is dominated by matrix multiplications. Trade-off: higher per-instance cost, requires batching to utilize fully. \textbf{TPU inference}: Google's custom accelerators, optimized for large batch, high throughput. Advantages: higher throughput-per-dollar than GPU for large batch inference, native BF16 support. Disadvantages: limited to Google Cloud, less flexible than GPU, poor for small batch/low latency. Use for: large-scale batch inference (daily recommendation updates), models already trained on TPU (TensorFlow/JAX ecosystem). \textbf{Decision framework}: (1) Model $<$ 10M params and no GPU-friendly operations: CPU. (2) Model $>$ 100M params, real-time serving: GPU with dynamic batching. (3) Model $>$ 100M params, batch inference at scale: TPU or GPU depending on cloud provider. (4) Edge/mobile: CPU or specialized accelerators (Apple Neural Engine, Qualcomm Hexagon).

\textbf{Red flags} (what NOT to say):
\begin{itemize}
    \item ``Always use GPU for ML inference''---CPU is often better for small models
    \item Not considering cost per inference (GPU is expensive when underutilized)
    \item Ignoring the batch size dimension (GPUs need batching to be efficient)
\end{itemize}

\textbf{What the interviewer is testing:} Hardware awareness. Do you know when GPU overhead is not justified? Can you reason about cost-performance tradeoffs?

\textbf{What separates good from great:}
\begin{itemize}
    \item \textbf{L5:} Correct CPU vs.\ GPU guidance, mentions model size as the key factor
    \item \textbf{L6:} Includes TPU tradeoffs, discusses dynamic batching, cost-per-inference analysis
    \item \textbf{L7:} Discusses specialized accelerators (inference ASICs like AWS Inferentia, Groq), compiler optimizations (TensorRT, XLA), and the total cost of ownership including engineering time
\end{itemize}

\textbf{Common follow-ups:} ``When would you use AWS Inferentia?'' ``How do you decide between A100 and H100?'' ``What about inference on Apple Silicon?''
\end{interviewq}

\begin{interviewq}
\textbf{Q: Build vs buy vs open-source---give a decision framework for ML infrastructure.}

\textbf{Difficulty:} L7 \quad \textbf{Type:} Trade-off \quad \textbf{Frequency:} \freqmed{}

\textbf{Strong answer:} This is fundamentally a strategic decision that depends on differentiation, team capability, and total cost of ownership. \textbf{Build custom} when: (1) the component is core to your competitive advantage (e.g., Google builds its own serving infrastructure because serving efficiency at their scale is a differentiator), (2) no existing solution meets your requirements (unusual scale, latency, or integration needs), (3) you have a dedicated platform team to maintain it long-term. Risk: high upfront cost, ongoing maintenance burden, opportunity cost of engineer time. \textbf{Buy (managed service)} when: (1) the component is commodity (experiment tracking, monitoring, basic serving), (2) speed to production matters more than customization, (3) you lack the team to maintain infrastructure. Examples: Weights \& Biases for tracking, Datadog for monitoring, SageMaker for managed training. Risk: vendor lock-in, cost at scale, limited customization. \textbf{Open-source} when: (1) the component is well-established with active community (MLflow, Airflow, Ray, vLLM), (2) you need customization but not from scratch, (3) you want to avoid vendor lock-in. Risk: operational burden (you own the deployment and upgrades), community priorities may not align with yours, security patches are your responsibility. \textbf{Framework}: For each ML infrastructure component (feature store, experiment tracking, model serving, training orchestration, monitoring), ask: (1) Is this a differentiator? If yes, build. (2) Does a good open-source solution exist? If yes, use it. (3) If neither, buy. \textbf{Common pattern at FAANG scale}: Build the differentiated core (serving infra, feature platform), open-source the non-differentiated components (Kubernetes, Spark), and avoid buying managed services for anything at massive scale (cost prohibitive).

\textbf{Red flags} (what NOT to say):
\begin{itemize}
    \item ``Always build''---ignores opportunity cost and maintenance burden
    \item ``Always buy''---ignores vendor lock-in and cost at scale
    \item Not considering the team's ability to maintain what they build
\end{itemize}

\textbf{What the interviewer is testing:} Strategic technical decision-making. This is a Staff+ question that tests whether you think about organizational impact, not just technical merit.

\textbf{What separates good from great:}
\begin{itemize}
    \item \textbf{L5:} Reasonable build vs.\ buy reasoning with cost considerations
    \item \textbf{L6:} Three-way framework with concrete examples, discusses vendor lock-in and total cost of ownership
    \item \textbf{L7:} Connects to organizational strategy (what is the company's competitive advantage?), discusses the migration path (start with bought/OSS, migrate to custom as scale demands), proposes a decision matrix for each infrastructure component
\end{itemize}

\textbf{Common follow-ups:} ``How do you migrate from a managed service to a custom solution?'' ``What is the true cost of maintaining open-source infrastructure?'' ``How do you make this decision at a startup vs.\ FAANG?''
\end{interviewq}
